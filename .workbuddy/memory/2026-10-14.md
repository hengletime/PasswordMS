## 🔴 桌面端"白屏"事件（D-18，未结案）

发现：`passwordms.exe` 窗口（1113x756，标题 `PasswordMS`）**客户区纯白**，前端完全没渲染。

### 先说教训（比结论更重要）

- **我此前声称"程序正停在创建保险库向导"是错的**——那是从"`%APPDATA%\com.passwordms.app` 目录为空"**推断**出来的，我**从没真正看过窗口内容**。目录为空只能证明"没建过库"，不能证明"界面渲染出来了"。
  → **铁律：声称 GUI 正常之前，必须真的看到内容（截图/PrintWindow），不能用侧写证据代替。**
  → 侧写证据（目录为空、进程存活、`Responding=True`、窗口有标题）**全都可以在"前端白屏"时同时成立**。`Responding=True` 只说明消息循环没卡死。

### 取证过程与证据

1. **内嵌资源没丢**：在 exe 里 grep 到明文 `assets/index-DMzPtqJZ.js` / `assets/style-D_k4BFOa.css` / `index.html`，与当前 `dist/` **逐名一致** → 排除"打包漏了前端"。
   - 方法：Tauri 的 phf 资源表**以明文存路径字符串**，可直接在二进制里 grep。这是个好用的排查手段。
2. **截图**：纯 Python + ctypes（`user32` BitBlt → GDI → 手写 PNG，`zlib`+`struct`）抓屏，无需任何第三方库。**`Add-Type` 被沙箱安全策略拦截**，所以 PowerShell 里造不出 P/Invoke，只能走 Python ctypes。
   - 脚本：`%TEMP%\pms_win_probe.py`（windows / cap 两个子命令）、`%TEMP%\pms_win_titles.py`
3. **WebView2 崩溃转储**：`%LOCALAPPDATA%\com.passwordms.app\EBWebView\Crashpad\reports\*.dmp`，共 **4 个**（约 7.9 MB/个），全部来自**我启动的实例**。
   - 崩溃签名（`Crashpad\watson_metadata`，ASCII 段可读）：
     ```
     ApplicationName=msedgewebview2.exe  ApplicationVersion=155.0.4283.45
     ModuleName=msedge.dll                ModuleVersion=155.0.4283.45
     ModuleOffset=187699613               ProcessType=browser
     SubCode=0x80000003                   ← STATUS_BREAKPOINT（Chromium 硬 CHECK / IMMEDIATE_CRASH）
     WV=passwordms.exe  WV_V=0.1.0
     ```
   - 三个 dump GUID：`73655c40e-…`(9:14:50)、`05a77ce23-…`(9:15:17)、`805339b47-…`(9:20:13)，第 4 个 9:31 左右。
   - `Crashpad\temp\edge_shutdown_crash.txt`、`Last Version=155.0.4283.45`。
4. **关键嫌疑：沙箱 DLL 注入**。`passwordms.exe` 的模块表里有
   `tsbx.dll` ← `…\WorkBuddy\resources\app.asar.unpacked\cli\vendor\sandbox\5.8.5\tsbx.dll`。
   **即使我把命令标成"禁用沙箱"启动，`tsbx.dll` 照样被注入**（WORKBUDDY 的注入不是按单条命令走，而是覆盖整棵进程树）。
   → 说明：**我无法在本机做一次"干净"的启动**，所以我也无法自证"程序是否真的有病"。
   - 另注：`EBWebView` 目录里更早（10-13 19:41、10-14 6:53）的痕迹存在，但**没有**对应时期的 dump → 佐证"崩溃与我的启动方式相关"。
5. **排除项**：进程存活、`Responding=True`、窗口标题/尺寸正常、WebView2 运行时 155.0.4283.45 已安装且 `SearchHost.exe` 的 WebView2 工作正常（同版本）→ 运行时本身没坏。
   - 非系统 DLL 里除 `tsbx.dll` 外只有 `EmbeddedBrowserWebView.dll`（Edge 官方）与 `ManualNewWord.dll`（搜狗输入法）。

### 结论与下一步

- **未定性**：白屏可能是①沙箱注入/拦截导致 Chromium browser 进程自毁，也可能是②真实的打包/配置缺陷。

- 已顺手做的：`npm run dev` 起在 1420（验证 devUrl 假设用），验证后需关闭。

### ✅ 结案（客户实测）

**客户在资源管理器里双击 exe，界面正常出来了** → 白屏确认是沙箱注入 `tsbx.dll` 导致，**不是产品缺陷**。

## 🔴 D-19/D-20/D-21：界面缺陷（客户截图报障）

客户实测截图反馈「创建保险库」页三处问题，我逐一在代码里定位并复现。

### D-19（P0 · 可用性致命）· `.field` 命名冲突 → 输入框与眼睛**纵向堆叠**
- 客户原话：「我每一次看到时不知道'主密码'要在哪里输入……我首先看到的是'至少 8 位'那几个大字，我以为要在他下面某个地方输入，可是没有找到。」
- 命中：`src/components/CreateVaultWizard.svelte:133`、`src/components/LockScreen.svelte:106`
- **机制（关键）**：`global.css:118` 有 `.field { display:flex; flex-direction:column; gap:.35rem; margin-bottom:.75rem }`；两个组件各自又定义了**同名局部** `.field { display:flex; align-items:center; border:...; padding-right:.25rem }`。
  Svelte 局部样式带 hash → 特异性 0,2,0 > 全局 0,1,0，所以 `display`、`align-items` 由局部胜出；
  **但 `flex-direction: column` 只存在于全局规则里、局部没覆盖它 → 直接漏过来**，
  于是输入框与眼睛按钮**竖着摞**，外面套一层边框，看起来就是个又高又怪的大框。
- 旁证：下面「确认主密码」没包在 `.field` 里，高度正常 —— 两个框长得不一样，正是这个 bug 的指纹。

### D-20（P0 · 语义反了）· 密码可见性图标方向错
- 客户原话：「眼睛闭上是显示星号、睁开是显示密码明文，你这好像反了。」
- 代码：`<Icon name={showPassword ? 'eye_off' : 'eye'} />` —— 隐藏态给"睁眼"，明文态给"带斜杠"，与国内 App 习惯相反。
- 4 处全中：`CreateVaultWizard:60`、`LockScreen:49`、`ItemDetail:207`、`ItemEditor:132`
- 应为：`name={showPassword ? 'eye' : 'eye_off'}`
