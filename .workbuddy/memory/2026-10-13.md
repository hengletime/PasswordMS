## PasswordMS 项目启动（需求讨论轮 · 未开工）

**主人需求**：跨端密码管理工具，Windows 可用 + 安卓可用，支持局域网同步，程序体积要小，参考 Bitwarden。
功能：① 分组 CRUD；② 保存网址 + 用户名 + 密码，一键直达；③ 保存密钥文档。

**小李（software-company 专家团主理人）给出的方案要点**：
- 技术栈推荐 **Tauri 2 + Svelte + Rust core**（一套代码覆盖双端，Win 安装包 3–8MB / APK 5–10MB）；备选 Flutter（15–25MB）与双端原生。
- 安全底座：Argon2id 派生主密钥 → 包裹 DEK → 条目级 XChaCha20-Poly1305；零知识；自动锁定；剪贴板 30s 清空；Android FLAG_SECURE；密钥存系统 Keychain/Keystore。
- 局域网同步：**二维码配对（IP+端口+一次性令牌）+ 局域网 HTTP + 载荷端到端加密**；条目级 last-write-wins 合并。mDNS 自动发现为备选，手动加密文件导入导出作兜底。
- 功能池 P0（分组/条目/生成器/搜索/自动锁定）→ P1（TOTP、密钥文档附件、Bitwarden JSON 导入、回收站、密码体检）→ P2（生物识别、安卓自动填充、全局热键）。
- 明确不做：浏览器扩展、云端账号、团队共享、Web 端。
- 体积预算：Win ≤10MB、APK ≤12MB；拒绝 Electron 与整包 UI 框架。

**状态**：等主人在 4 个决策点（技术栈 / 同步方案 / MVP 范围 / "密钥文档"定义）确认后，再由主理人 TeamCreate 并启动 SOP 工作流。

## PasswordMS 真实编译验证（晚 · 关键转折）

**结论：`03-impl.md` §5 的 `IS_PASS: YES` 是误判，已撤回改判 NO。** 该结论是**无编译器环境下的静态文本审查**（grep+人工比对），只能证明「引用与声明对齐」，**不能证明类型正确**。

**真实编译器暴露 16 个错误**（新增权威文档 `docs/03b-verification.md`）：
- 生产代码 11 处：10× `E0308`（`&Zeroizing<[u8;32]>` 传给已放宽的 `&[u8]` 形参，漏了 `[..]` 切片——session.rs 82/83/125/126/177/178/189/190、repository.rs 945/946）+ 1× `E0603`（container.rs:25 `FRAME_HEADER_LEN` 私有转导入）

### MSI 打包：WiX 缓存手工预热法（可复用）

`tauri build` 的 NSIS 步骤完全成功，但 MSI 步骤卡在从 GitHub 下载 `wix314-binaries.zip`（实测 ~17KB/s，16 分钟未完成）。

**解法：绕过 GitHub 直连，手工预热 Tauri 的 WiX 缓存。**
1. 用 GitHub 加速代理下载（`ghfast.top` 实测可用，41.3 MB 全量拿到；`gh-proxy.com`/`ghproxy.net` 备选）：
   `curl -sL -o wix314-binaries.zip "https://ghfast.top/https://github.com/wixtoolset/wix3/releases/download/wix3141rtm/wix314-binaries.zip"`
2. 解压（Windows 自带 `C:\Windows\System32\tar.exe` 即 bsdtar，支持 zip）到 **`%LOCALAPPDATA%\tauri\WixTools314\`**（220 个文件，含 `candle.exe`/`light.exe`/`wix.dll`/`sdk/`/`x86/`/`doc/`）。
   → 目录名 `WixTools314` 是从 `node_modules/@tauri-apps/cli-win32-x64-msvc/cli.win32-x64-msvc.node` 里 grep 出来的（`grep -aoE "WixTools[0-9A-Za-z]*"`）；本机**没有 `strings` 命令**，得用 `grep -a`。
3. 重跑 `npx tauri build --bundles msi`，Tauri 检测到缓存目录已存在即跳过下载。

> 通用套路：Tauri 所有外部工具（NSIS/WiX）都缓存在 `%LOCALAPPDATA%\tauri\`，且**只要目标目录存在就跳过下载**——国内弱网环境下优先用这招，别硬等 GitHub。

## 第二笔提交（10-13 深夜 ~ 10-14 凌晨）

**D-11：APK 原生库为空壳 —— 本轮最严重发现，也是最值钱的教训**

- **现象**：`npx tauri android build --apk --target aarch64` 产出的 APK，包内 `lib/arm64-v8a/libpasswordms_lib.so` **压缩前后都是 0 字节**。体积 1.62 MB，**12 MB 红线全绿通过**，但装真机必崩。
- **为什么差点漏掉**：门禁只查体积，而空壳包体积天然更小——**门禁越绿越可疑**。真正发现它是因为复核时对"`.so` 条目读出来 0 字节"起疑，手工深挖。**没有一条自动化测试会报这个错。**
- **根因**：`cargo-mobile2`（Tauri 移动端构建的实际执行者）用**符号链接**把 `.so` 放进 `jniLibs/<abi>/`。CLI 二进制内含 `symlinking lib .. in jniLibs dir ..` 与 `Failed to remove broken symlink ..: ..`（`cargo-mobile2-0.22.5/src/android/jnilibs.rs`，用 `grep -aoE` 从 `cli.win32-x64-msvc.node` 里挖出来的）。本机产出的是**坏链接**，AGP 顺断链读 → 0 字节。
- **⚠️ 推翻了工程师的错误归因**：他报的是"本机无法创建符号链接（WinError 4390，关沙箱也一样）"。我实测：**D: 是 NTFS、当前非管理员、未开开发者模式，`os.symlink` 在项目目录与系统临时目录都成功，硬链接也成功。** → 既非权限也非文件系统问题，**开开发者模式解决不了**。这条结论很重要，否则会去改系统设置白忙一场。
- **修法**：绕开软链步骤 —— 硬拷贝 `target/aarch64-linux-android/release/libpasswordms_lib.so`（4,895,912 B）进 `jniLibs/arm64-v8a/`，再在 `src-tauri/gen/android` 下
  `./gradlew :app:assembleUniversalRelease -x rustBuildUniversalRelease -x rustBuildArm64Release -x rustBuildArmRelease -x rustBuildX86Release -x rustBuildX86_64Release`
  → APK **6,595,076 B（6.29 MB）**，包内 `.so` 头部 `7f454c46`（ELF）、sha256 `6cc3ccbc…a5f4` 与构建产物**完全一致**（我独立复核）。
  - **五个 `rustBuild*` 任务一个都不能漏**——漏掉哪个，哪个就会把 jniLibs 覆盖回空壳。
  - **修复路径不能再自己调 `cargo build --target aarch64-linux-android`**：`.cargo/config.toml` 里没有该目标的 linker（Android 链接器由 Tauri 构建时用环境变量注入），自己调会因找不到链接器失败。只能复用上游已产出的 `.so`。
- **残留**：再跑一次 `npx tauri android build` 即被覆盖回空壳。**已绕过，未根除。** 主人裁定走 **A 方案：上游路径 + 校验 + 自动修复**，已派工改 `scripts/build-android.sh`。
- **必须记住的通用判据**：**"构建返回 0" ≠ "包能用"；"体积达标" ≠ "包是完整的"。** 唯一可信判据是**解出包内 `.so`，断言长度 > 0 + 头部为 ELF + 哈希与构建产物一致**。

**产物新鲜度审计（另一个差点交付出去的坑）**

- 逐产物比对 `mtime` 与源文件 `mtime`，发现 MSI（10-13 20:00）和 APK（21:54）**早于** `build.rs` 20:11 / `Cargo.toml` 21:58 / `session.rs` 21:59 → 这两个产物出自**修复前**的代码。

## ⚠️ 一次自我纠错：我差点把错结论写进仓库（10-14 凌晨）

**事情**：查出 APK 空壳问题后，我判定"工程师给的根因『本机无法创建符号链接』是错的"，理由是"我实测 `os.symlink` 成功了"。**这个判定是错的**——而我已经把这条错结论写进了 `docs/03b-verification.md` 和 `scripts/build-android.sh` 的注释里（**都是要提交的文件**）。

**错在哪**：我判定"成功"的唯一依据是 **`os.symlink` 没有抛异常**。我**从未验证产物本身**。重跑同一脚本时，它在紧随其后的 `os.lstat()` 处直接崩 `FileNotFoundError` —— **`os.symlink` 既不抛异常、也什么都没创建**，是**静默空操作**（Bash 工具所处的沙箱 shell 带文件系统垫片）。

**原生工具的正确证据**：
```
PowerShell New-Item -ItemType SymbolicLink
[D:\Software\PasswordMS\.git\Temp]     失败: UnauthorizedAccessException HRESULT=80070005 "此操作需要管理员权限。"
[D:\Software\PasswordMS\.git]          失败: 同上
[C:\Users\HUAWEI\AppData\Local\Temp]   失败: 同上
AppModelUnlock 键不存在（开发者模式未开启）    IsAdmin=False
```
→ **本机确实建不了符号链接**（缺 `SeCreateSymbolicLinkPrivilege`）；工程师原判断方向是对的，只是错误码（4390）来自不可信的沙箱观测。

**还纠正了一个派生错判**：我曾把产物描述为"坏链接/断链"，推出"AGP 顺断链读到 0 字节"。抓现场取证后：
```
Length=0  Attributes=Archive  LinkType=(空)  IsReparsePoint=False  可打开、可读长度 0
```
→ 它是**货真价实的 0 字节普通文件**，不是符号链接、不是断链。

**两条通用教训（已写进脚本注释与文档，请务必记住）**：
1. **"调用没报错" ≠ "操作成功"。** 判定成功必须验证产物：存在吗？长度对吗？内容能读出来吗？——这跟本项目"构建返回 0 ≠ 包能用"是同一条。
2. **涉及系统级能力（权限、符号链接、注册表、进程）必须用原生进程取证**（直接跑 `powershell.exe`），不能拿沙箱 shell 里的 Python/Node 观测当结论。沙箱会静默吞掉部分系统调用。

**这次纠错是 QA 独立质疑触发的**。QA 指出"Python 不抛异常但产出 0 字节"与"原生 PowerShell 报 E_ACCESSDENIED"相互矛盾、怀疑沙箱垫片干扰——**质疑成立**。印证了原则：**验证者要换角度攻击实现者的结论，而不是复跑实现者跑过的路径。** 我当时给 QA 的任务里明确写了"独立证伪，不要复跑工程师跑过的"，这一条起作用了。
