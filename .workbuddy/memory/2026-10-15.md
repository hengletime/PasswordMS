## D-46 配对真凶落网：Windows accept 继承非阻塞模式（傍晚）

- 主人升级桌面端后重测，新日志的 stage|io:Kind 一击致命：`hello_recv|io:operation would block` / `confirm_recv|io:operation would block`。带 30s 读超时的阻塞流绝不该返回 WouldBlock——唯一解释：accept 出的 socket 仍是非阻塞。
- 根因（平台差异，仅 Windows）：**Winsock 的 accept 会让新 socket 继承监听 socket 的非阻塞模式**（Unix 不会）。poll_accept_and_sync 把 listener 短暂设非阻塞轮询，accept 出的 stream 未改回阻塞 → recv 在数据未到时立即 WouldBlock → Host 中止 → 手机端读对端关闭 → 「文件读写出错」。
- 为什么回环测试从没抓到：127.0.0.1 投递零延迟，数据永远先于 recv 到达，竞态从不触发。**教训：测试环境零延迟会掩盖所有时序竞态，回归测试必须人为制造延迟。**
- 同时解释了报错变化：D-44 多 IP 修复已生效（手机能连上了），错误从 connect 超时类变成稳定的 io 中途断开。
- 修复：server.rs + resync.rs 两处 poll accept 后 `stream.set_nonblocking(false)`；新增回归测试 poll_accept_stream_is_blocking_after_accept（客户端延迟 600ms 发垃圾帧，断言 host 阻塞等待且错误非 WouldBlock），红-绿验证通过（stash 修复 → 测试红；恢复 → 绿）。
- 测试编写踩坑：poll_accept_and_sync 是单次轮询，测试必须循环调用，否则 server 被 drop、监听关闭、客户端 ConnectionRefused（浪费一轮排查）。
- 双端都重出包：手机端 resync 监听同样吃这个 bug（sync_now 入站方向）。
