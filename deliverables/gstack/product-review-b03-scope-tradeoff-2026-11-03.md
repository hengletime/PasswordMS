## 1. 四块拆解

### A · 换密隔离判据修正（已提交 `a158c9d`）

**做（保持）**
- 收益：旧备份不会被贴错标签。标签错的后果是用户按提示去开、打不开，而那是他最后一次尝试。
- 风险：无新增（成本已付，测试已绿，clippy 零告警）。

**不做（revert）**
- 收益：零（已花的工时不会回来）。
- 风险：`old-key/` 目录照样产生，但"哪份是旧的"判断在时钟异常时会失效且不报警——**一个错的判断比没有判断更糟**，因为它给用户一个明确但错误的标签。

> 结论：不适用，**保留**。

### B · 三层文案 + 旧代可见行

内容：换密成功页「只换锁、不换钥匙」；旧代栏「只防顺手牵羊，不防懂行的人」；第三层出口「怀疑泄露 → 新建空库 + 全量导入才是真作废」。约 9 条词条 × 4 语言（zh-CN / zh-TW / en-US / th）。

**做**
- 收益：用户第一次知道「改主密码 ≠ 旧备份作废」。这是产品的**核心安全承诺**，现在是错的。
- 收益：给出可执行出口，用户不会陷入「我无路可走」。事实上路是有的（新建库+导入在密码学上就等于换钥匙）。
- 风险：文案可能让用户觉得产品「不够安全」。但这是如实告知，措辞可中性；**沉默才是真的不安全**。
- 风险：如果 1.5.30 的「更换钥匙」按钮迟迟不上，用户会长期看到「本版本不提供」。属于观感问题，不是安全问题。

**不做**
- 收益：省约一天工时；换密页保持现状（只提示成功）。
- 风险 🔴：用户继续相信「我改了密码，旧的都作废了」。这个错误信念的代价是**他以为已经安全，实际没有**。
- 风险 🔴：这是四块里唯一「不做就等于持续输出一句假话」的一项。其他三项是「没做」，这项是「做错了」。

### C · `old-key/` 出口（计量 + 按批列出 + 单批删除）

现状核实：`old_key_usage()` / `clear_old_key()` / `old_key_inventory()` **实现都在、生产调用点为 0**（`src-tauri/src` 与 `src/` 全仓 grep `old_key` 零命中）。配额 `min(体积×12, 1GB)` 只算当前代，管不到旧代。

**做**
- 收益：目录可被看见、可被删。用户能释放空间，也能真正执行「我不再需要那一代」。
- 收益：为 1.5.30「更换钥匙」铺路——那时旧代只会更多。
- 风险：新增一个**销毁动作**。按批删是单向门，删错就是永久丢数据。缓解：二次确认 + 明确写「这是该批密码在本机的唯一副本」+ 不做自动删。
- 风险：界面多一个可能误点的按钮。缓解：与「删除当前代备份」并列而非同一按钮，两个确认框互指。

**不做**
- 收益：少一个销毁入口，少一处误删面。
- 风险 🟠：目录继续「看不见、删不掉、还在长」。换两次密码就翻倍（每次换密把整个当前代 rename 进旧代），且不计配额、不被 `make_room` 看见。Android 上备份目录在应用私有存储里，用户**根本进不去**，没有任何手动出路。
- 风险 🟠：对「因为怀疑泄露才来删备份」的人，这是安全相关的假信念——他点完「删除全部备份」，旧代还在，且旧密码能开。

### D · 整块下线（只发当前代备份，换密隔离不上线）

**做**
- 收益：本版范围最小，最快发版；少一套界面。
- 风险：`old-key/` 里若已有数据（换过密码的用户），下线后更没人管它。
- 风险：旧备份仍能用旧密码打开，而界面完全不提——等于 B 不做的加强版。

**不做**：即保持当前路线。

## 2. 两个容易被忽略的事实

**① 成本已经不在后端了。**
`a158c9d` 把判据、守卫、顺序、四类回执全部做完并测过。B 与 C 剩下的工作是词条 + DTO 字段 + 界面，属于「照着已有的算好的值画出来」。这也是为什么"边际成本低、收益高"——不是乐观，是位置决定的。

**② 「不做」不等于「保持现状」。**
`old-key/` 目录从 `a158c9d` 起就会真实产生。所以三个选项的真实含义是：
- B/C 都做 = 有个可解释、可管理的机制；
- 只做 B = 用户知道有这么回事，但仍然看不见、删不掉；
- 只做 C = 用户能操作一个他看不懂的东西；
- 都不做 = 磁盘上多了一个用户不知道、删不掉、还在长、旧密码能开的目录。

**没有"什么都不变"这个选项。**
