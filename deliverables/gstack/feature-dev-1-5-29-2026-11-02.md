## 1. 各成员核心结论

### 🔍 产品评审员
- **核心判断**：四项不能一个版本发。依据不是工作量而是**回滚性质**——B-02 是四项里唯一改密文帧格式的，一旦要回退版本，用户历史会被旧客户端覆盖成 `[]` 且无提示；而 B-03（备份）恰好是 B-02 的处置基础，必须先落地。B-01/B-03/B-04 的收益是**堵住每天都在发生的损失**，不依赖用户做任何新动作。
- **关键建议**：B-01 不加任何开关（给了关的选项，就会有人在共享电脑上被 `Win+V` 出卖）；B-03 默认开、路径不可配置；B-04 默认 **6 词**、范围 4–8（不给 3 词），并在**创建保险库向导**里给 3 个候选——那才是主密码真正被设定的地方。
- **一处推翻**：它最初提的「`last.bak` 用 hardlink 省掉整库复制」在我方架构上不成立（容器是原地追加写，hardlink 会指向同一 inode，追加写会把备份一起改掉）。已改为 `fs::copy` + 体积分档节流。

### 🛡️ 安全官
- **核心判断**：B-01 写成「先写文本、再补标记」有竞态窗口（两条 API 之间被轮询剪贴板的程序读走 = 未标记副本已进历史，且不可撤销）。必须单事务，且**标记先、文本最后**——这样失败时明文还没进剪贴板，fail-closed 不需要回滚。
- **关键发现（我方案里的真 bug）**：`fs::copy` 会**连时间戳一起复制**，所以备份文件的 mtime 恒等于源库 mtime。任何「用 mtime 排序/判新旧/判节流」的实现都会全体误判，且**在 Windows 上必现、在 Linux 上可能不复现**。这条直接导致我最初版本的三个测试失败，已彻底改为「只按文件名里编码的时间判断」。
- **另一条真问题**：换主密码后，旧备份是**用旧主密码加密**的。用户忘了新密码时去点「恢复」，输入的是新密码 → 打不开 → 用户会得出「备份是坏的」这个结论，而那正是唯一退路。处置：`post-rekey` 快照 + 把既有备份按 mtime 隔离进 `old-key/` 子目录 + 明确提示。

## 2. 最终裁决（1.5.29 生效，1.5.30 开工时原样取用）

### B-01 剪贴板敏感标记
| 项 | 决定 |
|---|---|
| 范围 | **全标，零例外**（密码 / TOTP / 用户名 / 配对码全走同一入口） |
| 枚举 | `Sensitivity` **取消**，只有一个 `write_secret(text)`；不设 `NonSensitive` 变体、不设白名单 |
| 写入顺序 | 私有格式标记 → 最后写 `CF_UNICODETEXT`；**单事务**（一次 Open/Empty/Set.../Close） |
| 失败策略 | fail-closed：`EmptyClipboard` 后报错，**绝不留下未标记的明文** |
| 清空 | `EmptyClipboard` + 只写私有格式，**不写空文本**（否则历史里多一条「空」） |
| 能力三态 | `Option<bool>`：`Some(true)` / `Some(false)` 走两套文案，`None`（查询失败）**静默**；布尔默认值一律不许兜底 |
| 文案 | ①`已请求系统不要把复制的内容记入剪贴板历史` ②`当前系统不支持此排除，复制的内容可能留在剪贴板历史里` ③ 配对码专用：只说「已设自动清除」，不提历史 |
| 文案禁区 | 「密码不会留在历史里」「到期清空会保护历史」「不记入历史，到期自动清除」（后者暗示历史会在到期时被删） |
| 平台细节 | Windows：`ExcludeClipboardContentFromMonitorProcessing` 写字符串 `"1"`（**不是 DWORD 1**）、`CanIncludeInClipboardHistory`/`CanUploadToCloudClipboard` 写 4 字节 0；Android：`ClipDescription` extras 置 `EXTRA_IS_SENSITIVE` |
| **发布阻断** | Win10 + Win11 `Win+V` 实视；Android 13/14 浮层实视。未验不许发 |

### B-03 本地滚动备份
| 项 | 决定 |
|---|---|
| 三类文件 | `bak.<yyyyMMdd>`（日备份 ×5）/ `last.bak`（×1）/ 事件快照（`pre-restore`×2，`post-rekey`/`pre-compact`/`pre-import` 各 ×1） |
| 位置 | `vault.parent()/backups`，**结构上不存在第二个落点**（建不出来就失败告警，禁止回落到私有目录） |
| 分类与排序 | **只用文件名里编码的时间**；`modified_ms` 仅展示，不参与任何判断 |
| 节流 | 日备份：当天首次 + 跨零点 1 小时保护；`last.bak`：>4 MiB 的库 60 秒窗口（小库每次写都刷新） |
| 节流状态 | sidecar `backups/.state`（跨进程、测试天然隔离），**不用静态变量**（并行测试会互相污染） |
| 失败 | 不阻断保存（fail-soft），但必须落 `BackupOutcome.error` → 可见警告，**不许静默** |
| 原子性 | `.tmp` → 长度校验 → `rename`；不留半成品 |
| 配额 | `min(库体积 × 12, 1 GB)`；保底 `last.bak` + 1 日备份 + 1 pre-restore；`last.bak` 永不主动丢 |
| 恢复期 | `RestoreGuard`（RAII）在 core 内暂停**全部**快照与轮转——事件快照也停（它尾部会 prune，可能删到正在读的源） |
| 换主密码 | `post-rekey` 的 mtime/时刻必须**严格大于**改密完成时刻；既有备份按「早于改密时刻」隔离进 `old-key/` |

## 5. 给 1.5.30（B-02 密码历史）的开工依据

- **六条 P0 硬约束**：类型级不含 `attachments`（独立 `ItemSnapshot`，不用 `Item`）、历史不进 `item_hash`/搜索/体检/列表 DTO、上限 5 条 + 总字节 256 KB、超限拒绝而不是静默裁剪、锁定后 `wipe_plaintext` 必须覆盖历史、**体检不得扫描历史**。
- **`ItemViewDto`**（详情 DTO）承载 `history`，列表 DTO 只给 `history_count`；后者是"上次读取时的值"，UI 不做实时事实、不加动画。
- **降级快照**：`custom_fields: Option<Vec<CustomField>>`，`None` = 未记录；UI 标「该版本未记录自定义字段」；从降级快照恢复**只覆盖密码/动态口令**；恢复确认弹窗必须写明本次恢复范围。
- **超限报错文案里不许出现「历史」二字**（用户删不掉它），只能是「备注太长」。
- 产品口径：5 份 / 256 KB / 详情页折叠行 / 历史记录数 5 条 / 排除回收站与冲突快照 / 换主密码不碰历史 / 无导出。
