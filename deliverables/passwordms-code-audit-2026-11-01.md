## 一、整体审计综述

### 1. 整体风险评级：**中**

本轮未发现新的主密码或条目密码明文落盘、高危弱加密算法、硬编码主密钥、明显解锁绕过、同步明文传输或账号密码日志输出。核心加密链路、会话锁定、同步重放防护、附件密文分片传输等区域的实现和现有测试整体较完整。

但当前仍存在一项优先级较高的同步一致性缺陷：**分组记录没有条目记录已有的冲突检测与 LWW 判定，双端同时修改同一分组时会发生直接覆盖，并可能因同步水位推进而不再回发本端修改。** 此外，备份恢复、头部扩容、附件垃圾回收和导入流程仍有异常路径下的一致性缺口。

### 2. 结论摘要

| 分类 | 结论 |
|---|---|
| 加密与密钥派生 | 未发现新的明显高危错误；Argon2id、XChaCha20-Poly1305、随机密钥及 AAD 绑定路径完整 |
| 解锁与生物识别 | 未发现直接绕过；生物识别解锁要求实际解密成功帧，空库和错误 VK 有防护 |
| 条目同步 | 已有冲突检测、删除墓碑、水位和回归测试；仍存在设备时钟偏移下的条件性风险 |
| 分组同步 | **确认存在双端修改直接覆盖问题，应优先处理** |
| 备份与恢复 | 已有 magic、整帧流校验及恢复前备份；但容器头校验和原子替换仍不完整 |
| 附件与压缩 | 正常路径测试覆盖较好；I/O 失败时 blob 内存索引与磁盘状态可能不一致 |
| 前端状态 | 冲突仲裁成功后不刷新条目列表和详情，可能展示旧数据 |
| 导入 | 有大小、条数与格式校验；失败后预览不可直接重试，批量写入不是事务性的 |
| 依赖 | npm 实际发现 4 项公告（3 低、1 中），均位于开发/构建依赖面；Rust 依赖公告未完成核查 |
| 可访问性 | 样式契约检查通过，但有 6 项浅色按钮文字对比度警告 |

### 3. 建议处理顺序

1. **优先**：分组同步覆盖、恢复备份容器头校验、恢复覆盖非原子。
2. **其次**：头部扩容持久化、blob 墓碑失败一致性、冲突仲裁后的前端刷新。
3. **随后**：导入失败恢复能力、依赖公告、浅色按钮文字对比度及功能增强。

## 二、已确认的问题

> 本节“已确认”指代码路径和触发条件可以明确建立，不代表每一项都已在真实设备上复现。断电、磁盘满和 I/O 故障类问题未做破坏性实测。

### F-01｜高｜分组同步直接覆盖，缺少冲突检测与版本裁决

- **类别**：安全相关的数据一致性缺陷／业务逻辑缺陷
- **位置**：`crates/passwordms-core/src/sync/merge.rs:207-248`，`apply_changes`
- **相关位置**：`crates/passwordms-core/src/sync/merge.rs:311-345`，`note_received_changes`

**问题描述**

活跃 `FOLDER` 变更在解密后只进行墓碑复活抑制，随后直接调用 `put_folder_direct(remote)`。该分支没有：

- 比较本地与远端的 `rev`、`updated_at`；
- 使用共同基准判断双端是否都独立修改；
- 调用条目分支已有的 `detect_conflict`；
- 为分组生成可仲裁冲突。

接收后，`note_received_changes` 会把已被覆盖成远端版本的本地分组识别为“同源”，并推进发送水位。这样，本端原先的独立修改可能不再回发。

**触发条件**

两台设备在共同版本之后分别修改同一分组，例如同时修改名称、图标、颜色、钉住状态或顺序，再进行双向同步。

**风险危害**

接收方的分组修改会被静默覆盖，且后续同步不一定能把被覆盖版本重新带回，形成用户难以察觉的数据丢失。与条目不同，用户没有分组冲突箱可恢复另一版本。

**测试缺口**

现有 `sync_conflict.rs` 和 `d109_conflict_hash.rs` 覆盖条目冲突及 `folder_hash`，未找到“双端同时修改同一分组”的端到端回归测试。

**处理方向**

分组同步需要与条目同级的冲突/版本裁决语义，并补充双端分组修改、删除与修改并发、仲裁后收敛测试。本报告不提供实现。

### F-02｜中高｜恢复备份未验证容器头和格式版本

- **类别**：业务逻辑缺陷／数据可用性风险
- **位置**：`crates/passwordms-core/src/store/container.rs:370-434`，`verify_frame_stream`、`restore_backup_from`
- **对照位置**：`crates/passwordms-core/src/store/container.rs:68-97`，`Container::open`
- **调用位置**：`src-tauri/src/commands/vault_cmd.rs:214-244`，`restore_backup`

**问题描述**

恢复前校验覆盖 magic 和记录区帧边界，但没有执行正常打开容器时的以下检查：

- `format_version` 是否受支持；
- `header_len == 0` 是否非法；
- 头部 JSON 是否可解析为 `Vault`；
- 头部字段及 KDF／加密方案是否具备可打开的基本条件。

因此，一个 magic 正确、帧流为空或边界合法、但头部损坏或版本不受支持的文件，仍可能被判定为可恢复并覆盖当前库。极端情况下，仅含正确 magic、`header_len=0` 且没有记录区的最短前缀文件即可通过当前 `verify_frame_stream` 的结构判断，却会在正常打开时被拒绝。

**风险危害**

恢复操作可能报告成功，但用户随后无法解锁新库。当前命令在目标已存在时会先创建 `.bak-<时间戳>`，所以通常仍有回滚副本；这降低了不可逆损失概率，但不消除“恢复成功后库不可用”的问题。

**测试缺口**

`restore_backup.rs` 已覆盖正常往返、非 vault、帧截断和错误主密码，没有覆盖坏头部 JSON、零头长和不支持格式版本。

**处理方向**

恢复接受条件应与正常打开容器的基本结构条件一致，并在替换当前库之前完成这些验证。

### F-03｜中｜备份恢复使用直接复制覆盖，不是原子替换

- **类别**：编码隐患／崩溃与 I/O 一致性风险
- **位置**：`crates/passwordms-core/src/store/container.rs:418-434`，`restore_backup_from`
- **相关位置**：`src-tauri/src/commands/vault_cmd.rs:223-243`

**问题描述**

校验完成后直接通过 `fs::copy(src, dest)` 覆盖现有保险库，没有使用同目录候选文件、候选文件完整性复核和原子替换流程。

**触发条件**

复制过程中断、磁盘写失败、存储设备异常或进程意外退出。

**风险危害**

目标库可能处于部分覆盖状态。恢复前创建的 `.bak` 是事后补救，不是当前库写入的事务保证；如果用户没有意识到备份副本的存在，恢复失败后的处置成本较高。

**处理方向**

恢复应与整库重写一样具备明确的“旧库完整保留或新库完整生效”边界，并增加中途写失败测试。

### F-04｜中｜头部扩容整文件重写后未同步落盘即重命名

- **类别**：编码隐患／掉电一致性风险
- **位置**：`crates/passwordms-core/src/store/container.rs:139-176`，`Container::update_header`
- **对照位置**：同文件 `269-315`，`rewrite_with_frames`

**问题描述**

头部容量不足时，代码把新头和全部帧写入临时文件，但只调用 `flush()`，随后立即 `fs::rename`。普通帧追加、原位写入及压缩路径已经使用 `sync_all()`，只有这一整文件扩容分支缺少同等的持久化动作。

**触发条件**

头部增长触发整库重写，并在重命名附近发生系统崩溃或断电。

**风险危害**

可能出现重命名结果已可见，而新文件内容尚未完全持久化的崩溃安全缺口。该分支也会影响头部密钥材料更新等关键操作，不能仅视为计数元数据问题。

**处理方向**

统一整文件替换的持久化顺序，并通过故障注入或断电模型验证，而不只验证正常重开。

---

### F-05｜中｜附件 blob 墓碑先删内存索引，再执行可能失败的写盘

- **类别**：业务逻辑缺陷／异常路径一致性风险
- **位置**：`crates/passwordms-core/src/store/repository.rs:595-603`，`tombstone_blob`
- **调用位置**：同文件 `1676-1691`，`gc_orphan_blobs`
- **对照位置**：同文件 `558-570`，普通 `tombstone`

**问题描述**

`tombstone_blob` 先执行 `self.blobs.remove(id)`，再调用可能失败的 `pwrite_frame`。普通记录墓碑已经采用“先写盘、成功后删内存”的顺序，blob 路径与之相反。

**触发条件**

孤儿附件 GC、彻底删除或压缩前置 GC 期间发生磁盘满、权限变化或其他 I/O 写失败。

**风险危害**

操作返回错误时，内存已认为 blob 不存在，磁盘却仍可能保留活跃帧。同一运行周期内的后续 GC 可能不再重试该索引项，造成内存视图与磁盘状态不一致；重开后又会按磁盘内容重新出现并进入维护流程。

**测试缺口**

现有附件 GC 和压缩测试覆盖正常路径及引用保活，未找到针对 `pwrite_frame` 失败的故障注入测试。

**处理方向**

统一内存状态提交与磁盘写入的成功顺序，并验证失败后可重试性。

---

### F-06｜中｜冲突仲裁成功后，前端条目列表与详情不刷新

- **类别**：明确 UI 状态一致性缺陷
- **位置**：`src/lib/stores/sync.svelte.ts:341-356`，`SyncStore.resolve`
- **对照位置**：同文件 `302-329`，`syncNow` 成功后会调用 `vault.load()`
- **界面位置**：`src/components/sync/ConflictPanel.svelte:66-73`

**问题描述**

仲裁成功后只调用 `loadConflicts()`，没有重新加载 `vault`。而后端的 KeepLocal、TakeRemote、KeepBoth 均可能修改现有条目或新增副本。

**风险危害**

冲突从冲突箱消失，但条目列表和详情仍显示仲裁前的数据。KeepBoth 的新副本也可能暂时不可见，直到用户执行其他触发加载的操作。用户可能据此误判仲裁没有生效，进而重复操作或作出错误编辑。

**测试缺口**

`src/lib/stores/sync.test.ts` 只覆盖选择状态和未选择拒绝提交，没有覆盖成功仲裁后的数据刷新契约。

**处理方向**

把“仲裁成功后业务视图同步刷新”纳入状态层契约和自动化测试。

### F-07｜中低｜导入是逐条落库，失败时可能留下未向用户说明的部分导入

- **类别**：业务逻辑缺陷／批量操作一致性风险
- **位置**：`crates/passwordms-core/src/import/mod.rs:170-226`，`import::apply`

**问题描述**

导入先逐组写分组，再逐条写条目，最后统一持久化计数。任一中途写入失败都会直接返回错误，已经写入的分组和条目不会回滚，也没有返回“已成功写入多少条”的结果。

**触发条件**

大批量导入期间出现磁盘满、写权限变化、库容量错误或其他中途失败。

**风险危害**

界面只看到导入失败，但库内可能已存在部分数据。用户重新执行时，去重逻辑可能把已导入部分计为跳过，使结果更难解释。现有数据不会因这一逻辑被覆盖，主要风险是部分完成状态不透明。

**处理方向**

明确导入是“事务式”还是“可续传的部分成功”语义，并让结果、界面和重试行为与该语义一致。

---

### F-08｜低｜导入执行前即删除预览缓存，失败后不能直接重试

- **类别**：工作流缺陷
- **位置**：`src-tauri/src/commands/import_cmd.rs:69-92`，`import_apply`

**问题描述**

代码先从未完成导入缓存中 `remove(preview_token)`，然后才获取会话锁并执行 `import::apply`。会话已锁定、写盘失败或校验失败时，该预览已经不在缓存中。

**风险危害**

用户无法针对同一份已解析预览直接重试，只能重新选择并解析文件。若与 F-07 同时发生，还会形成“部分数据已写入、原预览又丢失”的不透明状态。

**处理方向**

明确预览 token 的消费时机和失败后的生命周期，避免把短暂执行失败等同于用户已确认消费预览。

### F-09｜低｜浅色主题部分按钮文字对比度未达到 AA 正文阈值

- **类别**：可访问性问题；**不是安全漏洞**
- **位置**：`src/styles/global.css:36-63`，浅色主题按钮颜色令牌
- **实测来源**：`npm run check:css`

**问题描述与实测结果**

## 三、条件性风险与架构边界

以下事项有明确代码依据，但是否构成实际事故依赖运行环境或外部故障，不与上一节的确定性缺陷混同。

### R-01｜中低｜条目 LWW 依赖设备时钟

- **位置**：`crates/passwordms-core/src/sync/merge.rs:155-175`
- **现状**：无冲突时优先比较 `updated_at`，只有时间戳相等才用 `rev` 破平。
- **条件**：设备时钟明显回拨或不同步时，较高 `rev` 的远端修改可能因时间戳较旧而不被采用。
- **影响**：同步结果可能不符合用户对修改先后的直觉，并增加后续基准和冲突状态的解释成本。
- **边界**：双端基于共同基准的独立修改通常仍会进入冲突检测；本条不是“所有时钟偏差都会丢数据”。

### R-02｜中低｜回收站移动是多帧写入，失败时不是单事务

- **位置**：`crates/passwordms-core/src/store/repository.rs:1241-1276`，`delete_item`、`move_item_to_trash`
- **现状**：先写 TRASH 快照并更新内存，再墓碑化 ITEM；第二步失败时，第一步不会回滚。
- **影响**：I/O 故障下可能出现活跃条目和回收站快照并存、重试产生额外快照等状态。正常路径已有还原冲突守卫，但不能替代故障时的原子性。

### R-03｜中低｜Android SAF 导出只验证长度，且回读不可用时仍报告成功

- **位置**：`src-tauri/src/content_uri.rs:126-186`，`copy_from_file`
- **现状**：provider 不允许回读或无法读取 metadata 时，函数仍返回源文件长度；可读时也只比对长度，不比对内容。
- **影响**：兼容了限制性 provider，但“导出成功”并不总等于“已重新读取并验证备份内容”。异常 provider 或提交失败但长度未暴露差异时，备份可信性仍有残余风险。
- **边界**：这是代码中明确记录的兼容性取舍，本轮未在 Android 真机上复现新的导出错误。

### R-04｜低｜导入预览在解锁期间可累计，缺少 TTL 和数量上限

- **位置**：`src-tauri/src/commands/import_cmd.rs:17-64`、`src-tauri/src/state.rs:57-72`
- **现状**：每个预览持有完整明文条目和分组；锁定级联会擦除并清空，但解锁期间连续预览可累计至多份。
- **影响**：反复预览大文件会增加明文生命周期和内存峰值。单个文件已有 64 MB 与条目数限制，这不等于缓存总量有限。
- **性质**：内存与生命周期优化建议，不是远程利用漏洞。

### R-05｜架构残余｜前端 DTO 与 JavaScript 字符串不可按 Rust 零化模型理解

- **位置**：前端条目 DTO、编辑器及 IPC 返回链路；Rust 核心已有显式 `wipe_plaintext`。
- **现状**：解锁期间，条目明文会因列表、详情和编辑需要进入普通 JS 对象与字符串；JS 引擎不提供可靠的主动覆写语义。
- **影响**：锁定时的 Rust 清理不能证明 WebView 进程内所有历史副本立即物理擦除。
- **性质**：架构内存残余风险，不应简化成“增加一次清空即可彻底解决”的漏洞。

### R-06｜环境相关｜库文件权限主要依赖平台目录边界

- **位置**：`crates/passwordms-core/src/store/container.rs` 的创建与写入路径；`sync/identity.rs` 仅对身份文件显式设置 Unix `0600`。
- **现状**：保险库本身依赖 Windows 用户配置目录 ACL、Android 应用沙箱或便携目录自身权限，没有统一的库文件权限收紧逻辑。
- **影响**：便携模式放在公共目录、用户主动放宽 ACL 或备份导出到共享位置时，密文库及元数据的暴露面由外部环境决定。
- **边界**：密文库泄露不等于直接得到明文，但会增加离线主密码猜测和元数据暴露风险。

## 四、第三方依赖检查

## 五、优化与功能建议（均不是已确认漏洞）

### S-01｜可验证备份与恢复演练

在现有加密备份之上，提供备份时间、大小、格式版本和结构校验结果的一屏摘要，并引导用户定期进行“恢复到隔离位置并验证可打开”的演练。重点是让备份可信性可观察，而不是只显示复制成功。

### S-02｜统一的同步冲突中心

除条目外，把分组修改冲突、设备时钟异常和缺失附件状态纳入统一诊断视图。用户应能知道“哪一端、哪个版本、何时修改、当前采用哪一份”，减少静默覆盖和同步结果猜测。

### S-03｜批量导入结果明细与断点语义

导入完成后提供新增、合并、重复跳过、解析跳过和失败项的结构化摘要；失败时明确是否存在部分成功。该建议同时改善 F-07／F-08 的用户可解释性。

### S-04｜条目历史版本

对密码、用户名、备注和附件元数据的修改提供有限数量的本地加密历史版本，并允许查看和回滚。它可缓解误编辑、错误冲突仲裁和同步覆盖造成的损失；历史保留数量、压缩策略和同步范围需要单独定义。

### S-05｜故障注入回归套件

为磁盘满、写入中途失败、重命名失败、锁中毒、同步中断和 SAF 回读不可用建立非破坏性故障注入测试。当前正常路径覆盖较丰富，下一阶段最有价值的是证明异常路径的可恢复性。

## 六、本轮重点复核后未发现明显问题的区域

1. **敏感信息落地**：条目、备注和分组主体位于 AEAD 密文中；未发现账号密码直接写入日志或控制台。
2. **加密原语**：使用 Argon2id 和 XChaCha20-Poly1305，随机密钥和 nonce 路径未见 MD5／SHA1 被用于密码保护，也未见无 IV 的简单 AES 设计。
3. **密钥派生参数**：KDF 参数有上下限和钳制校验，异常头部参数不会无约束放大资源消耗。
4. **密钥管理**：未发现主密钥、盐或加密种子硬编码；VK 与主密码派生密钥职责分离。
5. **解锁控制**：错误主密码与部分损坏错误有统一处理；未发现通过 IPC 直接读取锁定库的旁路。
6. **生物识别**：VK 不返回 JS；开启时需要主密码；空库、错误 VK、改密和平台密钥失效均有专门防护。
7. **同步协议**：有序列号、时间窗、会话绑定、重放防护、分页上限和容量限制；附件过线保持密文。
8. **附件路径安全**：`blob_ref` 有 UUID 校验与 spool 路径穿越纵深检查。
9. **输入边界**：导入文件、条目明文、附件大小、附件数量、文件名和库容量均已有校验。
10. **列表异步状态**：`vault.load()` 已使用请求序号阻止过期响应覆盖新筛选结果。
11. **收藏与分组范围**：当前 `VaultStore.setScope` 同时写分组、收藏、未分组三个视图位；旧版“收藏被当前分组污染”的问题不应继续作为当前缺陷报告。
12. **日志内容**：日志以错误码、计数、状态和指纹为主；未看到账号、密码、备注或 VK 明文输出。

## 八、发布前仍需使用者确认的事项

1. 当前 Windows 发布链是否能稳定生成安装包，并消除本次桌面 DLL 链接阻断。

7. 对浅色主题的可访问性目标是“控件 3:1”还是“按钮文字也按正文 4.5:1”，需形成明确验收口径。

## 九、最终结论

PasswordMS 当前版本的核心安全设计没有发现新的明显高危倒退，现有测试对加密、会话、条目冲突、附件同步和正常业务路径覆盖较多。当前主要短板不在密码学，而在**同步记录类型之间的语义不一致，以及异常写入路径的事务和可恢复性不足**。

最先需要闭环的是 F-01：它能在正常双端编辑场景下静默丢失分组修改。其次应把备份恢复从“帧流看起来完整”提升到“候选容器确实可打开且替换过程原子”，随后再处理界面刷新、导入重试和依赖／可访问性问题。
