# PasswordMS 待解决问题分析与实施建议（供 WorkBuddy 执行）

> 日期：2026-10-31  
> 核查基线：v1.4.19、`docs/02-arch.md`、`docs/03-impl.md`、`deliverables/v1.4.19-verification-and-open-issues-2026-10-30.md` 及当前相关源码。  
> 验证边界：本文结论来自静态源码与文档核查，没有重新执行真机测试。凡标记“第一嫌疑”或“待验证”的内容，不得提前写成已确认根因。

---

## 1. 总体判断

当前不应继续把主要精力投入“HyperOS 按 UID 丢包”假设，也不需要回退同步版本、重写配对协议或恢复已经明确回退的自动同步。

源码核查发现了一条更直接、尚未排除的线索：

- `src-tauri/gen/android/app/build.gradle.kts:18,24` 已使用 `compileSdk = 37`、`targetSdk = 37`。
- `src-tauri/gen/android/app/src/main/AndroidManifest.xml:3` 声明了 `INTERNET`，但整个 Manifest 没有 `ACCESS_LOCAL_NETWORK`。
- Android 17 对 targetSdk 37 应用强制执行局域网访问权限，影响本地 TCP 发起、TCP 接收入站、UDP 单播、广播和组播。
- 已有同类 Android 17 / targetSdk 37 项目出现“监听已建立但没有 TCP、局域网连接超时”，在只补充并授予局域网权限后恢复的对照案例，与当前现象高度相似。

参考对照案例：

- DiPlay #425：https://github.com/shihabal3amri/DiPlay/issues/425
- Android 官方局域网权限说明：https://developer.android.com/privacy-and-security/local-network-permission
- Android 17 行为变更：https://developer.android.com/about/versions/17/behavior-changes-17

因此，**API 37 局域网权限缺失是当前第一嫌疑，但仍需小米 17 真机 A/B 验证，不能直接写成已确认根因。**

浏览器和微信输入法能够访问局域网，不能排除这一假设：它们使用不同 UID、不同权限状态和不同协议路径。

## 3. P0：先验证 Android 17 局域网权限

### 3.1 第一步：固定设备和权限证据

在小米 17、小米 11 上分别记录：

- Android 版本、API Level、HyperOS 完整构建号；
- 当前 APK 的 targetSdk；
- `ACCESS_LOCAL_NETWORK` 是否声明、是否授予；
- 对应 AppOps 的包级和 UID 级状态；
- 当前应用 UID，避免把不同安装实例的结果混在一起。

重点不是再查一次 `INTERNET`，而是确认**局域网权限的有效状态**。

同时确认旧版与当前版本的 targetSdk 是否发生过变化，避免把“旧应用版本可用”误当成“当前 targetSdk 37 不需要权限”。

### 3.2 第二步：制作最小权限诊断版本

诊断版本只改变权限适配，不同时修改同步协议、端口、超时和发现顺序：

1. 声明 `ACCESS_LOCAL_NETWORK`。
2. 在用户主动进入配对或同步功能时申请运行时权限。
3. 仅声明权限不算完成，必须实际获得授权。
4. 在未授权、已拒绝、授权后被撤三种状态下，给出不同于“网络超时”的明确状态。
5. 低于 Android 17 的设备保持原有权限流程，避免无意义弹窗。
6. 将权限状态加入诊断日志，但不记录任何密码库内容或配对密钥。

### 3.3 第三步：同机 A/B 验证

在同一台小米 17、同一 Wi-Fi、同一电脑服务端口下比较：

| 测试项 | 未授权诊断版 | 已授权诊断版 |
|---|---|---|
| 手机主动 TCP 连接电脑 | 记录 | 记录 |
| 电脑主动连接手机监听端口 | 记录 | 记录 |
| UDP 广播发送与接收 | 记录 | 记录 |
| 扫码配对完整流程 | 记录 | 记录 |
| 配对后再次生成二维码 | 记录 D-139 | 记录 D-139 |
| 配对完成后的设备列表 | 记录 D-140 | 记录 D-140 |

每次只切换权限状态，并重启应用进程，避免把其他改动误判为权限效果。

### 3.4 验收标准

只有满足以下条件，才能把当前网络问题归因于权限缺口：

- 未授权时稳定复现；
- 授权后手机到电脑、电脑到手机均恢复；
- UDP 发现恢复，或能够单独解释其剩余故障；
- 撤销权限后故障重新出现；
- 重新授权后再次恢复；
- 不需要清数据、卸载或重置网络。

如果授权后仍失败，再进入双端抓包和同 UID 对照实验，不应继续只靠 `dumpsys` 推测。

### 3.5 权限不能解决时的第二轮取证

按以下顺序缩小范围：

#### A. 同 UID 对照

诊断版分别用 Kotlin Socket 和现有 Rust 网络路径连接同一测试端口：

- Kotlin 通、Rust 不通：检查应用网络实现。
- 两者都不通：继续检查系统或链路。

#### B. 不同 UID 对照

在同一手机测试 LocalSend、KDE Connect 或简单原始 TCP 测试应用。

浏览器成功只能证明浏览器 UID 的 HTTP 路径可用，不能证明 PasswordMS 的原始 socket 路径可用。

#### C. 双端同步抓包

手机记录 `SYN-SENT`，电脑同时抓包：

- 电脑看不到 SYN：检查手机出口或中间链路。
- 电脑收到 SYN 且已回 SYN-ACK：检查返回路径或手机接收侧。
- 手机收到 SYN-ACK 但仍卡住：检查本机 socket 状态。

#### D. 完整 bugreport

在复现后立即导出，并附准确时间戳，避免 logcat 滚动覆盖。

“按 UID 丢包”只有经过这些对照后，才适合作为提交给厂商的结论。

### 3.6 同步诊断日志要求

建议增加用户主动开启、默认关闭、可一键导出的脱敏诊断能力。

应记录：

- 应用版本、Android API、ROM 构建号；
- 局域网权限声明、授权及有效 AppOps 状态；
- 网络类型、socket 阶段、错误类别、耗时；
- 监听启动/停止、TCP accept 计数；
- MulticastLock 获取/释放、UDP 收发计数；
- 候选地址数量、各阶段结果，不记录配对载荷。

不得记录：

- 主密码、VK、IK、会话密钥、身份私钥；
- 条目标题、账号、密码、备注、自定义字段；
- 附件明文和文件名；
- 原始二维码、配对令牌、同步帧和密文载荷。

IP、设备 ID、指纹等信息应掩码或散列。日志应有大小上限和保留周期，由用户通过 SAF 主动导出，不自动上传。

## 4. 绕过方案的真实价值

| 方案 | 判断 | 原因 |
|---|---|---|
| 应用分身／工作资料 | 可用于诊断，不作为正式修复 | 能改变 UID，帮助判断是否与 UID 有关，但引入新的资料和网络策略 |
| USB ADB 隧道 | 可作为开发者应急通道 | `adb reverse` 只覆盖手机访问电脑；反向需要相应 forward 和监听适配，不适合普通用户 |
| Chrome Custom Tabs 代发 | 伪方案 | 面向 HTTP 浏览，不是任意 TCP 协议代理，还会改变身份和威胁模型 |
| 改走 IPv6 | 可做对照实验，不能当权限绕过 | 本地 IPv6 同样属于局域网访问；个别 ROM 上可用不等于合规或普遍可用 |
| 改 UDP／QUIC | 不建议为此重写 | 当前 UDP 也不通；权限限制同时覆盖 TCP、UDP，重写传输成本高且未必有效 |
| Tailscale／中继 | 后续可选架构，不是当前修复 | 能绕开部分 LAN 可达性问题，但引入 VPN、账号或中继依赖，改变纯局域网产品边界 |
| 加密文件经 SAF 转移 | 值得作为离线兜底 | 不依赖局域网；但必须走合并语义，不能简单整库覆盖 |

参考资料：

- Syncthing 配置与传输：https://docs.syncthing.net/v1.29.3/users/config
- LocalSend 协议：https://github.com/localsend/protocol/blob/main/README.md
- Tailscale 连接类型：https://tailscale.com/docs/reference/connection-types

Syncthing 的优势是多地址、TCP/QUIC、发现和中继组合；LocalSend 仍以本地 TCP 和 UDP 发现为基础；Tailscale 的关键是虚拟网络与中继兜底。它们都不能证明“更换传输协议即可绕过应用权限”。

**当前不建议改变“静态地址直连 → UDP 发现”的总顺序。** UDP 当前同样失败，发现优先不会解决权限问题，只会改变等待时序。先补诊断数据，再决定是否需要并行候选或缩短陈旧地址等待。

## 5. P0：Android 卸载后的数据恢复

### 5.1 当前性质

这不是 Android 异常删除，而是当前明确配置了：

- `AndroidManifest.xml:18`：`android:allowBackup="false"`；
- `data_extraction_rules.xml`：云备份与设备迁移全部排除；
- `full_backup_content.xml`：旧版备份同样全部排除。

因此应把它定义为**安全策略与数据可恢复性之间的产品缺口**，不是简单打开一个开关就算修复。

Android 应用私有目录随卸载删除是平台正常行为。应用也不能依赖收到自身卸载广播或 `onDestroy` 来完成“卸载前自动导出”。

### 5.2 第一层：用户控制的加密 SAF 备份

这是主要保障：

- 支持导出到用户选择的 Documents、Downloads 或外置存储位置；
- 导出内容保持现有保险库加密形态，不生成明文备份；
- 提供备份时间、备份结果和恢复入口；
- 支持恢复前校验，避免损坏文件覆盖现有库；
- 对“卸载应用会删除未导出的数据”给出明确提示；
- 通过定期备份提醒和恢复演练提高可用性。

SAF 用户文档不依赖应用私有目录，适合作为卸载后的主要恢复手段。

### 5.3 第二层：可选系统备份

若决定启用 Auto Backup：

- 默认仍建议关闭云备份，由用户明确选择开启；
- 只纳入加密保险库及恢复必需的最小元数据；
- 排除日志、缓存、会话状态、临时文件和明文密钥；
- 配对身份与设备授权建议恢复后重新建立；
- 恢复必须保留主密码解锁路径，不能依赖不会随备份恢复的 Keystore 生物识别密钥；
- Auto Backup 有容量、执行时机和 ROM 实现差异，常见配额为每应用 25 MB，不能承诺“卸载前一定已经备份”。

官方参考：

- Auto Backup：https://developer.android.com/identity/data/autobackup
- 备份与恢复规则：https://developer.android.com/guide/topics/data/autobackup

### 5.4 验收标准

- 导出后的文件在卸载应用后仍存在；
- 重新安装后能凭主密码恢复；
- 错误密码、损坏文件和不兼容版本均安全失败；
- 恢复不会静默覆盖现有非空保险库；
- 云备份关闭时没有任何保险库或密钥进入云备份；
- 生物识别不可恢复时仍能通过主密码恢复；
- 配对身份恢复策略明确，不产生“旧设备仍被信任”的隐式授权。

## 6. P1：同步“已应用”回执

### 6.1 当前风险

`docs/02-arch.md` §3.13.8 已承认：

- 发送方在 send 成功后推进 base／水位；
- 如果接收方在 apply 落盘前崩溃，后续可能不再重发；
- 最终形成“对端存活、本端已删”的静默分歧。

`crates/passwordms-core/src/sync/protocol.rs` 当前 `Done` 没有携带接收端已应用版本确认；发送侧在发送后调用 `note_sent_tombstones`、`note_sent_changes`、`note_sent_base` 等推进状态，与文档描述一致。

### 6.2 推荐设计

1. 接收端先把变更及本地合并状态持久化成功，再发送应用层确认。
2. 确认内容应能对应到具体批次或记录的版本，而不是只有一个“本轮成功”布尔值。
3. 发送方只在收到并通过会话认证的确认后，推进对应 base 和发送水位。
4. 未确认数据保留并在下轮重发，继续依靠 merge 幂等消除重复。
5. 通过能力协商区分新旧端；旧端保持现有兼容路径，但不能宣称具备新的崩溃一致性。
6. 多页推送需要明确按页确认或最终累计确认，避免只确认最后一页。
7. 回执本身必须纳入现有加密信封、重放防护和会话身份校验，不能形成未认证的状态推进入口。

### 6.3 必须覆盖的崩溃注入点

- 收到 Push 后、apply 前崩溃；
- apply 落盘后、发送确认前崩溃；
- 确认已发出、发送方保存状态前崩溃；
- live 变更与墓碑分别覆盖；
- 附件 finalize 与条目确认之间中断；
- 连续两轮同步后两端记录、墓碑、附件均一致。

**Lamport/HLC 只处理事件排序，不能替代送达与落盘确认。** 不应把它作为该问题的单独修复方案。

## 7. 后续 backlog 的正确处理

### 7.1 压缩与墓碑

D-76 已实现容器压缩和 blob 墓碑物理回收，不需要重做。

`crates/passwordms-core/src/store/repository.rs` 当前仍保留已删除 ITEM/FOLDER 的最高 rev 墓碑，是为了删除传播和复活抑制，不是遗漏清理。

正确顺序：

1. 先完成已应用回执；
2. 能证明所有相关对端已确认删除；
3. 再研究已确认墓碑的安全回收。

不能仅根据本端 base 直接删除墓碑，否则陈旧对端可能让已删记录复活。

### 7.2 已仲裁冲突记录

按文档已经决定的“双阈值并集”保留：

- 最近 10 条；
- 或 30 天内；
- 取更宽的一边；
- 清理前向用户披露会删除审计线索。

清理时必须继续保护未仲裁快照及其附件引用。

### 7.3 D-70 Joiner 长期指纹

作为 P3 加法式协议增强即可：

- HELLO 可选携带 Joiner 长期身份公钥；
- 老端缺字段时继续留空；
- 不得再用临时 `joiner_pub` 计算长期指纹；
- 验证新端与新端、新电脑与老手机，以及重配对指纹稳定性。

它不影响当前配对和同步，不应插队到网络恢复之前。

### 7.4 读侧取消归一

当前用户可见行为已经正确，属于实现形状债，不是缺陷。

只有出现第四处文件选择入口，或读侧取消开始弹错时，才统一收口，避免为无可见收益的一致性改动扩大回归面。

## 9. 明确不建议采取的方向

- 不在权限 A/B 之前继续围绕 HyperOS 内核做大规模推测性修改。
- 不恢复自动同步，不默认增加前台常驻服务。
- 不把 `46879` 当作非法端口，不按临时端口区间过滤候选。
- 不用 Chrome Custom Tabs 代理现有私有同步协议。
- 不把 IPv6、UDP 或 QUIC 当作局域网权限绕过手段。
- 不同时改变权限、端口、发现顺序、超时和协议，否则无法定位有效变量。
- 不在没有已应用回执前删除 ITEM/FOLDER 同步墓碑。
- 不把整库文件覆盖当作多设备同步；离线文件兜底仍需经过合并与冲突语义。
- 不把构建、单测或发布哈希验证写成真机行为验证。
