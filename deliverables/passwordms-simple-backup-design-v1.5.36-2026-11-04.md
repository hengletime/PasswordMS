# PasswordMS 简单有效备份设计

- 适用版本：PasswordMS v1.5.36
- 文档日期：2026-11-04
- 设计原则：**有效、简单**
- 核心结论：**保留现有整库密文滚动备份，不新增去重、增量链、对象库或自动云同步；本机自动备份之外，只保留两份可带走的加密整库副本。**

## 1. 目标与边界

### 1.1 要解决的问题

1. 刚才误改、误删时，能退回最近一次写入前。
2. 几天后才发现问题时，能回到较早日期。
3. 恢复、导入、压缩、修改主密码等高风险操作失败时，有操作前副本。
4. 卸载应用、磁盘损坏或换机时，仍有独立副本可恢复。
5. 备份次数和占用空间有明确上限，不随编辑次数无限增长。

### 1.2 明确不做

- 不拆分密码库元数据与附件。
- 不建立内容寻址对象库、代际清单或增量恢复链。
- 不依赖密文压缩节省空间。
- 不在每次字段编辑、自动保存或每一帧写入时额外生成永久备份。
- 不自动上传网盘，不把多设备同步当作备份。
- 不改变 v1.5.36 已具备的恢复、改密隔离和备份失败警告机制。

## 2. 总体方案：两层保护

| 层次 | 位置 | 主要作用 | 保留策略 |
|---|---|---|---|
| 本机自动备份 | 密码库旁的 `backups/` | 日常误操作和关键操作回滚 | 使用 v1.5.36 现有滚动规则 |
| 外部加密副本 | 用户选择的其他目录、移动介质或其他设备 | 卸载、磁盘故障、换机后的灾难恢复 | 最新一份＋上一份，共 2 份 |

两层缺一不可，但职责必须分开：

- `backups/` 方便、自动，适合快速回滚；它与原库位于同一应用数据环境，不能独立抵抗卸载或磁盘损坏。
- 导出的 `.vault` 是完整加密容器，可以带走；它不需要频繁生成，但必须能在原应用数据消失后独立使用。

## 3. 目录与文件结构

### 3.1 本机自动备份：沿用现有结构

```text
<密码库所在目录>/
├─ <当前密码库文件>
└─ backups/
   ├─ bak.<yyyyMMdd>              # 日备份
   ├─ last.bak                    # 最近一次写入前
   ├─ pre-restore.<epoch-ms>      # 恢复前
   ├─ pre-rekey.<epoch-ms>        # 改主密码前，旧密码可开
   ├─ post-rekey.<epoch-ms>       # 改主密码后，新密码可开
   ├─ pre-compact.<epoch-ms>      # 压缩前
   ├─ pre-import.<epoch-ms>       # 导入应用前
   ├─ old-key/<epoch-ms>/         # 改密后隔离的旧密码备份
   ├─ .state                      # 备份时间、节流与健康状态
   ├─ .pinned                     # 用户明确保留的恢复点
   └─ .retention                  # 自动清理开关
```

这些是 v1.5.36 已有结构，不新增另一套目录。`.state`、`.pinned`、`.retention` 是辅助状态，不是独立备份；灾难恢复以完整密码库副本为准。

### 3.2 外部副本：只设一个普通目录

```text
<用户选择的外部位置>/PasswordMS-Backups/
├─ passwordms-<日期时间-A>.vault  # 最新成功导出
└─ passwordms-<日期时间-B>.vault  # 上一次成功导出
```

文件名中的日期时间只是建议的手工命名方式，用于区分新旧，不要求修改当前导出功能。外部位置由用户明确选择；不要在未告知用户的情况下自动复制到云端。

## 4. 备份触发条件

### 4.1 本机自动备份

| 触发时机 | 行为 | 控制次数的方法 |
|---|---|---|
| 普通写入操作前 | 尝试生成日备份，并刷新 `last.bak` | 一次外层用户操作只调用一次；日备份当天去重 |
| 当天首次写入前 | 生成 `bak.<yyyyMMdd>` | 同日已有则跳过；另设 1 小时最小间隔，避免跨零点连续生成 |
| 小库普通写入前 | 更新 `last.bak` | 固定同名覆盖，不积累历史文件 |
| 超过 4 MiB 的库普通写入前 | 更新 `last.bak` | 距上次成功刷新不足 60 秒则跳过 |
| 恢复前 | 生成 `pre-restore` | 固定槽位轮转 |
| 改主密码前、成功后 | 分别生成 `pre-rekey`、`post-rekey` | 固定槽位轮转；旧密码备份隔离 |
| 压缩前 | 生成 `pre-compact` | 固定槽位轮转 |
| 导入正式应用前 | 生成 `pre-import` | 只在整批操作边界生成一次，不按导入条目数生成 |

普通条目、分组、回收站、排序等操作继续使用现有写入前入口。关键事件快照不受日备份去重和大库节流影响，因为它们是破坏性操作的直接退路。

### 4.2 外部加密副本

不跟随每次编辑自动导出，只在以下节点手动导出：

1. 首次放入重要数据后。
2. 大批量导入、整理或删除完成后。
3. 修改主密码成功后。
4. 换机、重装、卸载或系统维护前。
5. 日常使用期间，根据现有“距上次成功导出已满 30 天”提醒补做一次。

这条规则把外部备份绑定到少数有实际价值的节点，而不是绑定编辑次数。日常小幅修改如果尚未导出，其灾难恢复点可能停留在上一次导出；这是“简单、低频率”策略的明确取舍。

## 5. 保留与清理规则

### 5.1 本机自动备份

继续执行 v1.5.36 现有规则：

- 日备份：最近 5 份。
- `last.bak`：1 份，成功生成新副本后替换旧内容。
- 恢复前快照：2 份，避免连续恢复时丢掉第一次恢复前的状态。
- 其他关键事件：每种 1 份，互不挤占。
- 自动清理默认开启，清理超过 30 天的当前代候选副本。
- `last.bak`、被钉住的副本和最新一份不按 30 天规则删除。
- `old-key/` 中需要旧密码的备份不按当前代规则自动删除，只能由用户明确清理。
- 常规备份配额为当前库体积的 12 倍，绝对上限 1 GB；达到配额仍无法腾挪时，备份失败必须可见。
- 用户钉住和旧密码备份属于明确保留项，不能为了凑固定总份数而自动删除。

### 5.2 外部副本

只保留两份，按以下顺序轮换：

1. 导出一份新文件，不先覆盖或删除任何已有副本。
2. 确认导出功能报告成功，且返回、显示的字节数大于 0。
3. 新副本成为“最新一份”，原最新副本成为“上一份”。
4. 此时才删除更早的第三份。
5. 如果导出失败、目标为 0 字节或无法确认写入结果，不删除任何旧副本。

因此，外部稳态占用约为两份加密库体积；导出过程中可能短暂出现三份，这是为了不在新副本可用前破坏旧退路。

## 6. 写入安全与失败处理

### 6.1 本机备份

沿用现有安全边界：

- 备份是完整加密容器副本，不另造明文备份。
- 使用临时文件、长度校验、同步落盘和重命名，避免把半成品当作成功备份。
- 备份失败不阻断正常保存，但必须通过状态和设置页警告让用户看见。
- 恢复和改密期间暂停普通备份轮转，防止删除正在使用的副本或混淆密码代际。
- 配额清理保留关键退路，不能为了生成新副本先把所有旧副本删空。

### 6.2 外部导出

- 导出前继续要求当前主密码验证。
- 只认实际写入结果，不把“文件选择框关闭”或“创建了目标文件”当作备份成功。
- 外部 `.vault` 虽为密文，仍应按敏感文件保管；它可用于离线密码猜测，不应公开分享。
- 外部副本不保存主密码；主密码遗忘后，备份本身不能绕过解锁。

## 7. 恢复流程

### 7.1 从本机恢复点恢复

1. 在恢复点列表中选择目标时间和类型。
2. 如果副本属于 `old-key/` 或改密前快照，使用与该副本对应的主密码；不要假定当前新密码能打开旧副本。
3. 在覆盖当前库前验证备份密码和备份可用性；密码错误时停止，当前库不变。
4. 当前库仍存在时，先生成 `pre-restore` 快照。
5. 如果恢复前快照失败，默认不直接覆盖；只有用户明确接受“没有自动回滚点”后才继续。
6. 使用现有原子替换流程完成恢复，并重新验证能否正常解锁。
7. 恢复后先检查条目数量、最近修改和关键附件，再决定是否继续编辑或删除其他备份。

### 7.2 从外部 `.vault` 恢复

1. 确认原库中仍有未导出数据时，优先再保留一份当前库副本；不要直接覆盖唯一现状。
2. 在锁定界面选择“从备份恢复”，选取外部 `.vault`。
3. 输入导出该副本时有效的主密码。
4. 密码或文件校验失败时停止，不修改当前库。
5. 恢复成功后检查数据完整性，再重新开始常规自动备份。
6. 原设备仍保留的其他外部副本不要立即删除，直到新环境已确认可用。

## 8. 空间与次数估算

设当前加密库大小为 `S`：

- `last.bak` 稳态只占约 `S`，不会随写入次数增加。
- 日备份最多约 `5S`，并且只在实际发生写入的日期产生。
- 事件备份按类型限量，与导入条目数量无关。
- 本机常规占用还受 `min(12S, 1 GB)` 配额约束；钉住项、旧密码备份及写入瞬时文件需单独理解，不能把它们承诺为永远计入同一硬上限。
- 外部副本稳态约为 `2S`，轮换时短暂接近 `3S`。

备份次数不由“修改了多少个字段”决定，而由“发生写入的日期数、外层操作次数和关键事件数”共同决定；其中只有 `last.bak` 会频繁刷新，但它始终原地覆盖。

## 9. 验收用例

以下用例用于验证设计与现有行为是否一致；本文仅完成源码核对和设计整理，未在本轮执行测试。

| 编号 | 场景与操作 | 预期结果 |
|---|---|---|
| A01 | 小库连续完成多次普通编辑 | 每次外层操作尝试刷新 `last.bak`，但磁盘上始终只有 1 份；日备份不随编辑次数增加 |
| A02 | 同一天多次写入，随后跨日期再写入 | 当天只保留一个日备份；跨日期生成新日备份，并遵守 1 小时跨零点保护 |
| A03 | 持续产生超过 5 个有效日期的备份 | 未钉住日备份只留最近 5 份，较旧副本按轮转清理 |
| A04 | 小库与大库分别连续写入 | 小库每次写入前刷新 `last.bak`；超过 4 MiB 时 60 秒内不重复刷新 |
| A05 | 连续执行恢复、压缩、导入和改密 | 每类关键事件有自己的恢复点；恢复前最多 2 份，其他每种 1 份，不互相挤占 |
| A06 | 改主密码后查看并恢复旧备份 | 旧密码备份被隔离并明确提示密码代际；使用错误密码不能恢复或覆盖当前库 |
| A07 | 模拟备份目录只读、空间不足或配额不足 | 主业务按现有设计不被旁路备份拖死；设置页出现可见失败状态，不把失败显示成成功 |
| A08 | 使用错误密码恢复，或选择空文件、损坏文件 | 恢复在覆盖前停止，当前库内容和可解锁状态不变 |
| A09 | 恢复前快照失败 | 默认阻止无回滚点的覆盖；只有用户明确承担风险后才允许继续 |
| A10 | 导出外部副本成功后再次导出 | 确认第二份成功后才清理更早副本；外部稳态只余最新和上一份 |
| A11 | 外部导出失败或产生 0 字节目标 | 不记为成功，不删除已有外部副本，界面给出可识别失败信息 |
| A12 | 将外部副本与原应用数据隔离后，在干净环境恢复 | 仅凭 `.vault` 和对应主密码即可解锁并看到导出时的数据，不依赖原 `backups/` 辅助文件 |

## 10. 最终实施建议

### 对 v1.5.36 的直接结论

**本机备份核心无需为本方案重做。** 当前版本已经具备触发去重、固定槽位、大库节流、关键事件快照、配额、钉住、旧密码隔离、失败警告和安全恢复等能力。

最小落地方式只有两项：

1. 保留并验证现有本机自动备份，不再叠加第二套备份系统。
2. 把“外部最新一份＋上一份”作为简单操作规范执行；新导出确认成功前，不删除旧副本。

如果后续要增加产品功能，优先考虑提升外部副本状态与恢复指引的可见性，而不是增加备份格式。任何新增自动化都应先证明它不会在上传失败、路径变化或改主密码后制造“看似有备份、实际不可恢复”的新风险。

## 11. 本版源码核对依据

本设计按 v1.5.36 当前源码整理，主要依据：

- `crates/passwordms-core/src/store/backup.rs`：三类本机备份、节流、保留、配额、状态与恢复安全。
- `src-tauri/src/commands/backup_cmd.rs`：外层用户操作边界和关键事件入口。
- `src-tauri/src/commands/vault_cmd.rs`：加密整库导出、导出字节数与恢复校验。
- `src/lib/backup-reminder.ts`：成功导出记录及 30 天提醒。
- `src/components/Settings.svelte`：导出交互和备份状态展示。
