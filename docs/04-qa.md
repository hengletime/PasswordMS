## 8. 缺陷清单（按严重度排序）

### 🔴 D-1（高）· A-04 未真正达成：**锁定后解密条目明文未清零**

- **现象**：`Session::lock()` 仅把状态置 `Locked`，依赖 `Unlocked`/`Repository` 被 Drop 来“级联清零”。但**被解密的条目明文以普通 `String` 常驻内存**，Drop 时**仅释放内存、不覆写**。
- **证据**：
  - `crates/passwordms-core/src/model/item.rs:16-31` —— `LoginData` 的 `title/url/username/password/notes/totp_secret` 与 `SecureNoteData.body`（`:35-38`）**均为普通 `String`**，未用 `Zeroizing`；
  - `crates/passwordms-core/src/store/repository.rs:67` —— `items: BTreeMap<String, Item>` **在内存中保存解密后的明文条目**；`:188`（`rebuild_index` 解密后 `items.insert`）与 `:541/:557/:569/...` 均写入明文 `Item`；
  - `crates/passwordms-core/src/securemem.rs:14,17` —— `SecretString`/`SecretBytes` **已定义却全项目无引用**（grep 仅命中定义处）；
  - `crates/passwordms-core/src/session.rs:143-145` —— `lock` 只做枚举赋值。
- **影响**：攻击者若能 dump 已释放堆内存（崩溃转储 / 内存取证 / 后续分配复用），**可能恢复密码、备注、TOTP 密钥明文**。直接违反安全需求 §3.2「不得依赖『作用域结束即回收』……须显式擦除」。
- **测试为何没抓到**：`tests/zeroize_check.rs:26-46` 只查状态枚举与 `ERR_NOT_UNLOCKED`，**无任何字节级断言**。

## 2. 任务 1 · 错误码一致性探针（新增 `tests/unlock_error_probe.rs`）

**做法**：造合法库 → 拷贝并对**字节级**施加不同损坏 → 用**正确主密码**去 `Session::unlock`，
打印返回的错误码。除「错误密码」用错密码外，其余损坏均用正确密码，以隔离“是不是密码错”。
（**未改生产代码**；探针为纯新增测试。）

**实测原始输出**（`--test unlock_error_probe -- --nocapture`，实测通过）：

```text
==== A-05 解锁错误码实测（用正确主密码去解，除①外）====
① 错误密码            -> ERR_UNLOCK_FAILED
② 头部内容篡改(verify_mac) -> ERR_UNLOCK_FAILED
③ 结构性损坏 magic    -> ERR_INTERNAL
   结构性损坏 version  -> ERR_INTERNAL
   结构性损坏 header_len=0 -> ERR_INTERNAL
   结构性损坏 截断文件  -> ERR_IO
```

**结论：主理人的怀疑成立 —— 是真缺口（登记 D-10）。** 完整因果链：

- 需求 `docs/01-security-req.md:155`：A-05「解锁失败提示**不区分**『密码错 / 数据损坏』，**文案一致**」。
- 代码路径：`session.rs:107` `unlock()` 在 KDF 之前先调用 `session.rs:112` `Container::open(path)?`；
  该 `?` 把 `Container::open` 的错误**原样向上抛**，**根本走不到** `session.rs:130` 的
  `verify::unlock_check(...)`（后者才是被统一映射为 `UnlockFailed` 的地方）。
- 而 `Container::open`（`container.rs:68`）在结构校验失败时返回的是**各自不同的**错误：
  - `container.rs:77` magic 不符 → `Internal("bad magic")` → `error.rs:132` → **`ERR_INTERNAL`**
  - `container.rs:81` 版本不符 → `Internal("unsupported format")` → **`ERR_INTERNAL`**
  - `container.rs:85` `header_len==0` → `Internal("zero header")` → **`ERR_INTERNAL`**
  - `container.rs:74` `read_exact` 截断 → `Io(...)` → `error.rs:130` → **`ERR_IO`**
  - `container.rs:89` header JSON 反序列化失败 → `From<serde_json::Error>`（`error.rs:184`）→ **`ERR_INTERNAL`**
- 于是：**密码错 / 头部内容被篡改 → `ERR_UNLOCK_FAILED`；结构性头部损坏 → `ERR_INTERNAL` / `ERR_IO`**。
  攻击者只需把文件头改一个字节，即可从错误码**区分**“这个文件是不是本产品的库 / 是不是被结构性损坏”，
  与 A-05「文案一致、不区分」的**明文要求相冲突**。

**严重度评估：中低。** 泄露的是“**是否为结构性损坏 / 是否为本产品容器**”，**不**泄露密码正确性、不泄露密钥。
但它**确实**违反 A-05 的字面验收；修复成本极低（见下方建议）。

**修复建议（供工程师参考，本阶段不代改）**：在 `Session::unlock` 中把 `Container::open` 的
「结构性错误」也**折叠为 `UnlockFailed`**（或至少折叠为**同一个**错误码），例如：

```rust
let container = Container::open(path).map_err(|_| CoreError::UnlockFailed)?;
```

（`NoVault`（文件不存在）按现有语义可保留——它对应“无库”，与“解锁失败”是不同用户场景；此点是否需
一并折叠请产品/架构裁定。）

**探针的“特征化断言”设计（防止缺口被悄悄改回）**：`unlock_error_probe.rs:128` 对上述结构性损坏路径

本文档 D-10 结论**。这是**书面记录 + 回归护栏**，**不是**对该缺口的认可。

## 3. 任务 2 · 时序侧信道测试（新增 `tests/timing_sidechannel.rs`）

**抗时序的“结构性保证”**：解锁的**任何失败路径都不允许在 Argon2id 之前提前返回**。
Argon2id(m=64MiB, t=3, p=1) 是解锁耗时的绝对主项（本机 debug 下 ~1.9 s），任何“提前 return”
都会比完整 KDF 快上千倍、一眼可辨。故测试断言分两层：

1. **【结构性·对负载不敏感】**「错误密码」与「数据损坏」两条失败路径耗时的**中位数**，
   都必须 **≥ 完整 KDF 基准耗时的 50%**（证明两条路都真跑了 KDF）。
2. **【统计性·宽松】** 两条失败路径中位数的**比值**落在 **`[0.7, 1.4]`**（去预热、取中位数）。

为避免与其它测试并行抢 CPU 干扰计时，**本文件单独成一个测试二进制、且仅含这一个用例**；
`WARMUP=3`、`MIN_N=15`、`MAX_N=40`、目标每路径采集 ≈8000 ms（据此自适应 N）。

**实测原始输出（最近一次，`--test timing_sidechannel -- --nocapture`）**：

```text
[timing] Argon2id 基准中位数 = 1890.0 ms；每路径 N = 15（目标≈8000ms）
[timing] 错误密码   : N=15 median=1868.4ms p10=1771.1 p90=1935.0
[timing] 数据损坏   : N=15 median=1877.6ms p10=1788.7 p90=2048.7
[timing] 比值(wrong/corrupt) = 0.995；KDF 基准 = 1890.0ms
test result: ok. 1 passed ... finished in 75.53s
```

**两次独立运行的稳定性数据**：

| 运行 | KDF 基准 | 错误密码 median | 数据损坏 median | 比值 | 结果 |
|------|---------|----------------|----------------|------|------|
| 第 1 次 | 1786.6 ms | 2027.6 ms | 2111.2 ms | **0.960** | PASS |
| 第 2 次（本节） | 1890.0 ms | 1868.4 ms | 1877.6 ms | **0.995** | PASS |

- 两次比值 0.960 / 0.995 均**稳落 `[0.7, 1.4]`**；
- 两条失败路径 median 均 **≈ KDF 基准（1868/1878 vs 1890 ms，达 99%）** → **结构性断言铁证**：
  两条路径都跑满完整 Argon2id，**无任何提前返回**；
- **结论：代码在“错误密码 vs 数据损坏”上无显著时序差异，A-05 的时序面（对这两条路径）成立。**

> ⚠️ **边界说明（勿夸大）**：本测试**只覆盖**「错误密码」与「头部内容损坏」两条失败路径。
> 对**任务 1 所述的结构性损坏路径**（`ERR_INTERNAL`/`ERR_IO`），因其在 `Container::open` 处
> **KDF 之前**就返回，耗时**显著更短**（毫秒级）——这既是 D-10（错误码可区分）的**同源**问题，
> 也是一处**可测的时序差异**。修复 D-10（折叠错误码）时应**同时**确保这些路径**不再早退**，
> 否则仍留有“结构性损坏比密码错快上千倍”的时序侧信道。此项**已列为 D-10 修复验收的一部分**。

## 1. D-17 事实陈述（现象 / 危害 / 机制）

- **现象**：`npx tauri android build --apk --target aarch64` 产出的 APK 里，`lib/arm64-v8a/libpasswordms_lib.so` **压缩前后均 0 字节**（无原生代码的空壳包）。
- **危害**：**致命**。空壳包因少了 4.89 MB 原生库，体积**反而更小**（≈1.62 MB），12 MB 红线**更容易放行** → **门禁越绿越可疑**；装真机必崩。
- **机制（更正后表述）**：Tauri 经 `cargo-mobile2` 把原生库放进 `jniLibs/<abi>/` 时**依赖创建符号链接**；而**本机创建符号链接被系统拒绝**（非管理员 + 开发者模式未开，进程不持有 `SeCreateSymbolicLinkPrivilege`）。结果是 **`.so` 位置留下一个货真价实的 0 字节普通文件**——**不是符号链接、也不是断链**；AGP 把这个**真实存在的空文件**打进 APK，包体因此缺失原生代码。
  > ⚠️ **不使用「断链 / broken symlink」描述产物形态**。CLI 二进制里确有 `Failed to remove broken symlink` 之类字符串（见 §1.1-b），但那是 **CLI 自身的错误处理措辞**，**不代表最终产物形态**；产物形态以 §1.2 的原生取证为准。

## 3. 校验的能力边界与死分支（如实登记）

**F1（死分支，轻微）**：`verify_apk` 里「条目长度为 0」分支（`scripts/build-android.sh:240-244`）在本实现下**不可达**。因为 `extract_entry`（`:172-212`）**只有在产出文件非空（`[ -s ]`）时才 `return 0`**，故成功路径的 `size` 恒 >0，「长度为 0」这条永远轮不到。**证据**：用例 2（0 字节条目）命中「缺失或为空」（`:233-236`），而非「长度为 0」。
→ **不构成漏洞**（坏包仍被判失败），但该分支是**误导性死代码**，建议删除或改写注释。

**F2（能力边界，重要）**：`verify_apk` 只断言「存在 / 非空 / 前 4 字节 = `7f454c46`」，**并不把解出的 `.so` 的 sha256 与 `$REAL_SO` 比对**——它只把 sha256 `ok` 打印出来（`:250-256`），**不做相等断言**。**证据**：用例 EX-B 是一个 100 字节、以 `7f454c46` 开头的垃圾文件，sha256 与真实库**不同**，却**返回 0 通过**。
→ 后果：**任何 ABI 名字对、带 ELF 头的文件都能过门禁**（例如陈旧/错误构建、被截断的 ELF）。当前交付包的真实性（哈希一致）是**人工核对**出来的，**不是脚本保证的**。
→ 建议（增强，非阻塞）：在 `verify_apk` 增补一条 **`sha256(解出 .so) == sha256($REAL_SO)`** 断言，把「是正确构建产物」也纳入门禁。

## 4. 口径（**唯一判据**）

> **「构建返回 0」与「体积达标」都不是包能用的证据。唯一判据是：解包后 `.so` 的（i）条目存在、（ii）长度 > 0、（iii）前 4 字节为 ELF `7f454c46`、（iv）哈希与真实构建产物一致。**

其中 (i)(ii)(iii) 已由 `scripts/build-android.sh` 的 `verify_apk` 强制；(iv) 目前**靠人工核对**（本阶段已核对通过），**未进门禁**（见 §3-F2）。
