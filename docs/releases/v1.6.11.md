# PasswordMS 1.6.11

这一版只改一件事：让「检查更新」在网络上不那么容易失败，失败时也说清楚是哪一类失败。

## 先说结论：上次失败不是程序坏了

我们拿同一台机器、同一时段，连着请求了六次 GitHub 的版本接口：

| 次数 | 结果 | 耗时 |
|---|---|---|
| 1、2、5、6 | 连接失败（超时或连接中断） | 10 到 20 秒 |
| 3 | 成功，配额还剩 58/60 | 0.5 秒 |
| 4 | 403，但同时报配额还剩 58 | 0.3 秒 |

六次里成功一次。成功那次配额是充足的，说明不是"请求次数用完"；能成功也说明不是被墙。同时段发布脚本上传同一个安装包，也是先失败两次、第三次才过。

所以是这条线路到 GitHub 接口端点的通断在抖。程序本身没有算错，但它有两个可以做得更好的地方：一次失败就放弃、以及失败只给一句"请稍后重试"。

## 这一版改了什么

**失败自动重试两次，间隔一秒。** 抖动是间歇性的，重试能救回大部分失败——发布脚本靠的就是这个。

**失败原因分三类说。** 以前只有一句"检查失败，请稍后重试"，用户不知道该等还是该换网。现在：

- 连不上 → 告诉你已经自动重试过，可以换条网络，或者直接点下面的下载按钮
- 被 GitHub 限流 → 告诉你通常一小时左右自动恢复，不让你以为程序出毛病了
- 其它 → 仍然是原来那句"请稍后重试"

**失败时多给一个不经过接口的兜底。** 「前往下载」按钮直接用浏览器打开 Releases 页——接口端点在抖的时候，浏览器往往还能打开。

**限流这一类我们不重试。** 配额是按小时恢复的，重试只会多打两次请求、还让你多等两秒。这条有专门的单测守着。

**自动检查仍然静默失败。** 后台每天最多查一次，查不到就不吭声，绝不会因为网络抖动弹一个提示打扰你。

## 已知限制

- 重试只在同一条网络内进行。如果整条线路都不通，三次都会失败，这时仍需要换网络。
- 限流判定依据 HTTP 403/429。GitHub 若改用别的拒绝方式，会被归到"其它"。
- 这一版没有改「自动检查」的节流策略（仍是 24 小时最多一次）。

## English summary

PasswordMS 1.6.11 hardens the built-in update check against flaky networking.

Six consecutive requests to the GitHub releases API from the affected machine produced four connection failures (10 to 20 second timeouts), one success with 58 of 60 requests still in the rate-limit budget, and one contradictory 403 that also reported remaining quota. The release upload script hit the same pattern in the same period, succeeding only on its third attempt. So the failure was network jitter, not a defect in the version check — but the app gave up after one try and reported every failure with the same vague message.

This release therefore retries twice with a one-second pause, which recovers most intermittent failures. Failures are now classified: unreachable network, GitHub rate limiting, or anything else — each with its own message telling the user whether to wait, switch networks, or simply use the download link. On failure the settings page also offers a "Get the new version" button that opens the releases page in the browser, bypassing the API entirely.

Rate limiting is deliberately not retried, since the quota recovers on an hourly basis and retrying would only add requests and make the user wait longer; a unit test pins this behaviour. Automatic background checks still fail silently, so network jitter never produces a popup. Known limitations: retries stay on the same network path, and rate-limit detection relies on HTTP 403 or 429 responses.
