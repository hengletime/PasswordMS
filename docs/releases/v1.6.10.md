# PasswordMS 1.6.10

这一版只干一件事：修一个"把文件夹改了名，结果主密码和指纹都登不进去"的现场。

## 现场说了什么

用户把便携绿色版所在的文件夹改了个名字，之后打开程序，主密码不对、指纹也不灵。听上去像是"改名把库弄坏了"，但我们查下来，库一点没坏。

## 先说不是什么（这三条都验过）

**不是便携标记丢了。** `passwordms.portable` 和 `passwordms.vault` 都还在，日志也确实写在改名后的目录里。

**不是程序算错了程序目录。** 新进程报告的 exe 路径就是改名后的那个目录，没有落到别处。

**不是改名破坏了加密。** 库的记录区 152 帧完整、尾部零残余，`vault_id` 与指纹封印一致，把 `mac_check` / `wkv_check` 按当前库头重算，结果与封印里存的逐字节相同。

我们还做了一次直接的对照实验：自己建一份密码已知的测试库，**改名前后各登录一次，两次都一次就进了主界面**。

## 真正的原因：改完名之后，点错了门

便携版的数据落在程序旁边，安装版的数据落在系统的应用数据目录。这是两个完全不同的位置，可以装着两份内容不同的库——而两个界面长得一模一样。

现场那台机器上就是这样：便携版那份 70 条，安装版那份 58 条，两者库身份相同、盐也相同，但包裹密钥和校验值不同，说明中途改过主密码，两份停在了不同的密码代上。安装版那份的指纹封印还绑着一个早已不存在的库身份，所以那份库按指纹必然失败。

链条是：改文件夹名 → 开机自启项里存的旧路径失效 → 重启后没有程序自动起来 → 用户去点桌面图标 → 那是安装版 → 打开的是系统目录里那份库 → 两把钥匙都对不上。

## 这一版改了什么

**解锁页最底部会显示当前数据目录。** 字很小、颜色很淡、排在所有按钮下方——它是需要时才去查的信息，不是每次解锁都要读的提示。路径只显示末尾两段，完整路径鼠标悬停可见。

**如果发现另一处还躺着一份库，解锁页会明确说出来**，并告诉你"如果你要找的是那份，请从那个位置启动程序"。这一条不淡化：它必须被看见，否则这次修复等于没做。

**解锁失败终于会写日志了。** 界面上仍然是一句统一的"解锁失败，请重试"（这是刻意的，防止有人靠错误提示的差异去试探），但本机日志会记下真实的错误码。之前失败一句日志都不留，出了问题只能靠猜。

**便携版说明书加了一段"改名 / 搬移文件夹"**：先彻底退出程序（点右上角的叉只是收进托盘）、整个文件夹一起搬、搬完把旧的桌面图标删掉。

## 已知限制

- 数据目录那一行只显示末尾两段，路径很长且末尾两段重名时，需要悬停看完整路径。
- "另一处还有库"的判据是"上一次启动用过的那个目录里仍有保险库"，不扫全盘。如果两份库都很久没用过，可能不提示。
- 开机自启项在改文件夹名之后**不会自动更新**（这一版没改这里，只补了文档说明）。如果改了名发现开机没自动启动，手动开一次程序、或重新勾一次设置里的开机自启即可。

## English summary

PasswordMS 1.6.10 fixes a field report where renaming the portable app's folder appeared to break the master password and fingerprint unlock.

Nothing cryptographic was broken: the vault's 152 records were intact, the vault id still matched the biometric seal, and both seal check values recomputed byte-for-byte identical. A controlled experiment — the same vault, the same known password, logging in before and after the rename — succeeded both times.

The real cause was a wrong entry point. The portable build keeps its vault next to the executable, while the installed build keeps a different vault under the system application-data directory. On the affected machine both vaults existed and had diverged onto different master-password generations. Renaming the folder invalidated the stored auto-start path, so nothing launched at boot; the user then clicked a desktop shortcut that pointed at the installed build, and ended up entering their portable password against a completely different vault.

This release therefore makes the situation visible: the unlock screen now shows the current data folder as a quiet footer line, and explicitly warns when another vault is found elsewhere, telling the user to launch from that location instead. Unlock failures are now written to the local log with their real error code (the UI message stays intentionally generic), and the portable build's readme explains how to rename or move the folder safely.

Known limitations: the footer shows only the last two path segments; the "another vault" check is based on the previously used folder and does not scan the whole disk; the auto-start registry entry is not automatically repaired after a rename in this version.
