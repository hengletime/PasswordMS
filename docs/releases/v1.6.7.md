# PasswordMS 1.6.7

这一版没有新功能，全部内容来自 1.6.6 的真机走查反馈：五处「看起来能用、实际不对」的地方。加密方案与库文件格式一个字节都没动，旧版升上来直接能开。

## 一边删分组、一边改名字，同步后分组不再复活

上一版有个难看的形状：A 端删掉分组「工作」，B 端在删除之前把它改名成「公司」，然后同步——**没有冲突提示**，B 的改名直接盖过去，A 端那个已经删掉的分组活过来变成了「公司」。

根因不是概率问题，是「谁先发起同步」决定的。删分组时写下的那枚墓碑，记录里的版本号**停在删除前那一刻**（删除本身不推进版本号），而改名会把版本号加一。所以只要由 B（还活着的那一端）先发起同步，A 收到的就是一个「比我的删除更新」的版本，代码当时直接照单全收。

现在这种情况会进冲突箱：两端各出现一条「分组」冲突，B 那边标着「远端已删除」，A 那边标着「本端已删除」，名字左边是删除前的样子、右边是改名后的样子，你选自哪一边就按哪一边收尾。仲裁「确认删除」会真的再删一次（把墓碑的版本号顶到对方之上），否则这个决定传不到另一台设备，两边会各自以为自己是对的。

顺带修了一处同源问题：你在 B 上点完「采用远端」，A 那端原本留着一条早就处理完的陈旧卡片，得自己再点一遍才消失。现在它会跟着一起收口。

## 「常用条目」终于真的是常用

快速唤出浮层时，钉住的条目一直排在最上面（这是对的），但下面那些没钉住的，顺序看着和「常用」没关系。

查下来排序本身没错，是**使用次数从来不长**：全程序只有「复制密码」会记一次使用，而**从浮层里直接自动输入的那一次，一次都不记**。日常几乎都走浮层，于是「常用」永远是 0，未钉住区只能退回到按最近修改时间排。

现在自动输入成功也记一次使用。另外走查单里那句「反复复制几次把使用次数拉高」也改掉了——后端有 60 秒节流，一分钟内连点只算一次，按原话操作很容易得出「频率没生效」的错觉。

## 主窗口就在眼前时，热键不再叠一块小窗

以前不管主窗口在不在前台，按一下全局热键都会在屏幕中央再弹一个快速搜索小窗。人正对着主窗口，又被压上一块窗，视线得挪开再挪回来。

现在分四种情形：小窗已经开着 → 再按就收起；主窗口在前台 → 什么都不做；主窗口开着但被别的程序盖住或最小化了 → 把它拉回前台；主窗口收进了托盘（不在屏幕上）→ 这时才弹小窗。

自动输入热键的行为**没有改**：焦点在本软件自己的窗口里时，它仍然不弹浮层，也不提示。这是防「密码被打进自己的编辑框」的安全判据，按你的要求维持静默。

## 冲突卡的确认按钮不再横贯整条

那张卡片里「确定」被拉成了一整条色块。不是按钮的问题，是卡片是纵向排布、按钮作为直接子项被拉满了宽度。现在它按内容宽度、靠右。

## 回前台指纹卡片：这一版仍然要你在真机上验

先说清楚：我们**没有**拿到安卓真机，这一条不能算修好。这一轮做的是把前两次失败的根因查到底，并堵住两处会让人「怎么切都没反应」的坑。

查明的第一件事：那张卡片只有在一个地方会变——系统是否还录着强档生物特征（指纹 / 人脸）。而「已开启」这个状态读的是我们自己写的封印记录，你去系统设置里删指纹、加指纹，**都碰不到它**。所以必须**把指纹与人脸全部删光**，卡片才会掉档；只删其中一枚、或者手机上还留着别的人脸，卡片不动是正常的。走查单原来那句写法会让你把正常行为判成缺陷，已经改掉。

第二件事：回前台的刷新只挂在两条同源的事件上，而且那行代码把「有没有发出去」的结果直接丢掉了——所以前两轮（1.6.4 挂错层、1.6.5 改挂窗口事件）都只能靠猜。现在加了第三条腿（页面可见性，程序里自动锁定一直在用、真机上长期有效），给合并闸门加了 3 秒安全阀（查询卡住时不会把之后每一次切回都挡在门外），发事件成功与失败都写进日志。

**怎么取证**：如果这次还是不变，请看数据目录里 `passwordms.log` 有没有 `[resume] 已发出 app://resumed` 这一行。有，说明宿主的通知到了、问题在界面侧；没有，说明宿主那条腿没走，靠页面可见性兜。

## 已知限制

- **回前台刷新这一条没有真机验证**（见上）。这一版只保证链路不再只赌一个信号、并且留下可查的证据。
- 删分组与改名撞车时，**两端各有一条冲突**，需要在两端各自看过。这是有意的取舍：只在一端显示，另一端就会「同步了什么也没发生」。任一端的裁决都会正确传给对方。
- 条目侧有同型的「本端已彻底删除、远端又更新」路径，本次**没有**改。原因写在架构文档 §3.32.5：条目删除先进回收站，回收站条目仍算活着，触发面窄；而条目冲突是三选一（含「两者都留」），删除-复活要重新裁定语义，不该塞进这一单。
- 「常用」统计口径从「复制」扩到了「复制 + 自动输入」。同一分钟内反复使用同一条仍然只算一次（节流）。

## English summary

This release has no new features. All of it is real-device feedback from the 1.6.6 walkthrough: five places that looked fine but were not. The crypto scheme and the vault file format are untouched, so upgrading from an older version just works.

- **Deleting a folder on one device while renaming it on the other no longer resurrects it.** The delete tombstone kept the version number it had before deletion, so when the surviving device initiated the sync, the rename simply overwrote the delete. This is now a two-sided conflict you resolve explicitly; resolving it as "confirm delete" re-stamps the tombstone above the losing version so the decision actually reaches the other device. A stale conflict card left behind after the peer resolves is also closed now.
- **"Frequently used" now reflects actual usage.** Usage was only counted when copying a password; passwords injected straight from the overlay were never counted, and that is how people normally use the app. Autofill now counts too. The walkthrough step that said "copy it a few times" was wrong anyway — there is a 60-second throttle per item.
- **The global hotkey no longer stacks a quick-search window on top of the main window.** If the main window is focused, nothing happens; if it is covered or minimized, it is brought back; only when it is hidden to the tray does the small window appear. The autotype hotkey is unchanged and stays silent when focus is inside PasswordMS itself.
- **The confirm button in the conflict card is no longer stretched across the whole card.**
- **Biometric card refresh on resume is still unverified on a real device.** We found two concrete problems: the card can only change when the set of enrolled strong biometrics changes (so all fingerprints and face must be removed), and the refresh relied on two copies of the same event with the emission result discarded, which is why two earlier attempts could not be diagnosed. A third signal (page visibility) was added, a 3-second watchdog on the refresh gate was added, and emission success/failure is now logged as `[resume] 已发出 app://resumed`.

Known limits: folder delete-vs-rename produces one conflict on each device by design; the item-side equivalent path is deliberately not changed in this release; and the biometric refresh still needs a real-device check.
