# PasswordMS 1.5.34

接着 1.5.33 收两个尾巴：**老备份的密码归属还是可能标反**，以及**首次启动偶尔整页英文**。

## 老备份也要判对

1.5.33 给备份加了一个「密钥世代号」，靠它判断某份备份该用哪把密码打开。问题是：这个号码从 1.5.33 才开始写，之前拍的备份里没有。没有号码时只能回落到「文件在哪个目录」——而恢复是整库覆盖，那一刻目录位置必然是错的，于是分组又全反了。

这一版补上第二级判据：**拿备份文件头和当前库的头部比一个校验值**。

那个校验值是主密码与盐派生出来的，等于「用这把密码能不能打开」的指纹：同一把密码配同一个盐必然同值，换过密码指纹就变。而恢复是把整库原样复制，所以刚恢复出来的那一份，头部与当前库逐字节相同 → 判回「用现在的密码」。比较用的是常数时间比较，不看内容只看相等。

最终判定顺序，按可信度从高到低：

1. **世代号**——最准，直接比数字；
2. **头部校验值**——备份和当前库各算一份比相等；
3. **目录位置**——`old-key/` 之类，旧行为兜底。

前两级只要有一级能给答案就不再往下走。三级都拿不到材料（比如极老格式连校验值都没有），才回落到目录位置，并接受它可能标反。

## 首启语言不再靠猜

现象：某个版本第一次打开，界面是英文。

原因不是缺翻译。程序启动时要决定用哪种语言，原来的做法是问 WebView 要 `navigator.language`。这个值在 WebView2 的档案目录还没就绪时会返回 `en-US`——不是「系统是英文」，是「现在答不上来，先给你个默认值」。更糟的是，那次检测的结果**没有存回去**，所以每次启动都在重新赌一遍。

现在改成两条：

- **问系统，不问浏览器**：走 Win32 的 `GetUserDefaultUILanguage` 再转成语言标签，这是操作系统的真实设置，不受 WebView 状态影响。
- **问完立刻存**：结果马上写进本地设置，下次启动直接读记录。只要用户自己选过语言，永远以用户的选择为准，绝不被覆盖。

这个检测只在「本地没有任何语言记录」时跑一次，且只在主窗口跑（快捷搜索小窗不参与，避免两个窗口抢着写）。

## 已知限制

- 三级判据对**极老格式**（头部连校验值都没有）仍无材料，只能回落到目录位置。
- 第二级在一种情况下会判得偏保守：配对同步时对方重封了密钥、但主密码本身没换——指纹会变，这份备份被判成「要用保存时那把密码」。方向是保守的：输现在这把照样打得开，只是提示多问一句，不会把人锁在外面。
- 1.5.33 之前拍的备份仍然没有世代号，只能走第二级。

## English summary

Backups created before 1.5.33 now get the right password label as well: when the key-generation number is absent, the header `verify_mac` is compared against the current vault (equal value means the same password). Decision order is generation → verify_mac → folder location. First launch no longer trusts `navigator.language`: the app asks Win32 for the system UI language and persists the result immediately, so a transient `en-US` from WebView2 can no longer leave the UI in English.
