# PasswordMS 1.6.4

这一版把三处「看起来没事、其实没兜住」的地方补严：自动输入注入失败时那段明文不再留在内存里；同步中止原因必须先通过认证才采信；附件同步遇到「两台设备不是同一个保险库」时，会说出真正的原因而不是笼统的「加密操作失败」。

## 自动输入：注入失败时，明文不再留在内存

自动输入是把当前这一条的内容逐字符送进目标窗口的。为了让 Windows 的 Unicode 注入接口能读，程序会先把整段文字转成 UTF-16 字节缓冲，送完再擦掉。问题出在顺序上：如果中途某个字符送不进去（目标窗口被切走、目标程序拒绝模拟按键等），函数会立刻返回，后面那句「擦掉缓冲」根本不会执行；而普通的字节数组在离开作用域时不会自动清零。也就是说，**越是失败的那一次，明文越可能原封不动地留在进程内存里**。

现在这段缓冲改用离开作用域就强制清零的容器来装。无论注入成功、中途报错，还是发生异常展开，缓冲都会被擦掉；「送不进去就立刻停下，不再继续灌后面的字符」这条安全行为原样保留。这是内存层的防护，界面上不会多出新的提示，也不需要用户做任何设置。

## 同步中止原因：不再凭一句明文就照做

1.6.2 加过一件事：同步做到一半的一方如果放弃，会把失败原因当成一帧发给对端，让两台设备显示同一个提示，避免一台说「加密操作失败」、另一台说「文件读写错误」。那条帧是**明文、不带认证**的：任何能往这条连接上写东西的人，都可以伪造一个原因。多数原因只是让人白忙一场，但其中一条会建议用户「导出保险库、到另一台从备份恢复」——照着一句来路不明的话去做整库换血，风险不小。

1.6.4 改成：中止帧必须带上会话、序号、时间、随机数和消息认证码，认证码用一把从同步密钥单独派生出来的子密钥计算，与正常数据加密用的密钥分开。先验认证，才允许根据帧里的原因产生任何提示；缺字段、字段长度不对、认证码不符、时间越窗，一律只回「同步已中止」，绝不回显或记录对方给的原因码。握手阶段的拒绝帧保持原来的线形不变，认证字段只加在数据阶段的中止帧上。中止处理仍然不写任何同步水位或游标，不会把一次失败的同步记成成功。

## 附件同步：终于说人话

1.6.1 已经能在两台设备的保险库密钥不一致时，当场提示「这两台设备里的数据不是同一个保险库」，并拦住配对。但那条判据只落在记录合并这一条路上；附件（图片、文件）走的是另一条解帧路径，同样的密钥不一致在那里仍被翻成「加密操作失败」，用户根本看不出该去导出/恢复。

这次把附件解帧路径上的「包裹密钥解不开」单独映射到同一个原因。校验很窄：**只有**包裹密钥解不开才改写码；附件内容本身缺片、错序、校验失败仍报「加密操作失败」，不会被误说成「库不一样」。至此，记录与附件两条路遇到同一个根因时给出同一句话。

## 已知限制

- **与 1.6.2 / 1.6.3 混用时，中止原因可能显示为通用提示。** 老版本发的中止帧没有认证字段，而 1.6.4 无法区分「老版本不会发」和「有人把认证字段剥掉了」，所以它选择一律不采信，只显示「同步已中止」。两端都升到 1.6.4 才能恢复「两端显示同一个具体原因」。1.6.1 及更早版本本来就不发中止帧，不受影响。反方向（1.6.4 中止、对端是老版本）不受影响，老版本仍能看到具体原因。
- 附件同步在收齐分片阶段发生的失败，仍不经过中止帧通道，两端提示不一定完全一致；这一版只统一了「密钥不一致」这一个原因。
- 这三处改动**都还没有在真机上走过一遍**。自动输入需要在 Windows 上实际触发一次注入失败；同步需要两台设备分别做「两端都是 1.6.4」和「一台 1.6.4、一台 1.6.3」两组；附件路径需要带一条含附件的记录做跨库同步。
- 自动输入的内存擦除不改变任何可见行为，也没有开关；它只能减少明文在进程内存里的停留，不等于防内存取证。
- 不做两个保险库的合并（1.6.1 起的老规矩，不变）：密钥不一致时，请留一台为准——在那台「导出保险库」，到另一台「从备份恢复」，然后重新配对。

## English summary

This release tightens three gaps that were invisible from the UI. First, Auto-Type used a plain byte buffer for the UTF-16 form of the entry being typed; if a keystroke injection failed, the early return skipped the explicit wipe and the buffer was never zeroed on drop. The buffer is now held in a zeroizing container, so success, early return and unwind all clear it, while the existing "stop immediately when injection fails" behaviour is unchanged. Second, the abort frame introduced in 1.6.2 carried a plaintext reason code with no authentication; a forged frame could suggest a destructive "export this vault, restore it on the other device" remedy. Abort frames now carry session, sequence, timestamp, nonce and a MAC computed with a dedicated HKDF-derived subkey, separate from the AEAD key. Authentication is verified before any reason is acted upon; missing fields, bad lengths, MAC mismatch or an out-of-window timestamp all collapse to the same generic "sync aborted" error, and the raw code is never echoed or logged. Handshake-stage reject frames keep their original wire shape, and abort handling still writes no sync watermark. Third, when two devices have different vault keys, the blob/attachment decryption path still reported a generic crypto failure while the record merge path already reported "not the same vault". The wrapped-key unwrap failure is now mapped to the same specific error; corrupt or missing blob parts still report a crypto failure.

Known limitations: when a 1.6.4 device talks to a 1.6.2 or 1.6.3 device, the older peer's unauthenticated abort frame is deliberately not trusted and only a generic "sync aborted" message is shown — both ends must be on 1.6.4 to see the same specific reason. 1.6.1 and earlier never sent abort frames and are unaffected. Blob-finalize failures still bypass the abort frame channel, so the two ends may not agree. None of the three changes has been verified on real hardware yet. Vault merging is still not supported.
