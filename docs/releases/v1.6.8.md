# PasswordMS 1.6.8

这一版只修一处：在冲突箱里点完「确定」之后，页面上的「待同步」会立刻变成 1，让你看得见「还欠一次同步」——不必再靠「对面怎么还没删」自己去猜。

## 裁决完，另一台设备为什么还没变

1.6.7 的真机走查里，这一条被记了下来：A 端删掉了分组，B 端把它改了名，两端同步后进冲突箱；在 A 上选「保留本机」= 确认删除，卡片当场消失，但 **B 端的分组还在，必须再同步一次 B 才会跟着删**。

先说清楚哪一半不是缺陷。裁决是**本端库里的一次写**：把那条删除记录的版本号顶到输掉那一方之上，再重新落一次删除。整个过程不发任何网络请求——同步协议里没有「裁决完主动推给对端」这条通道。另一台设备只能等下一轮同步，这与你平时改一个条目、对面也要等同步才看得到是同一件事。想让它当场就变，等于要求后台常驻一条推送连接，与「手动同步、不在后台偷偷联网」的设计前提冲突。

真缺陷在界面上：裁决成功后，程序只刷新了条目列表和冲突箱，**没有刷新同步状态**。于是「待同步」还停在 0。你看到卡片消失，自然会认为「这件事完了」，剩下那次同步只能靠自己反推。这属于老问题——**不会自动消失的状态，必须让人看得见**。

现在裁决一完成，「待同步」当场从 0 变成 1。点过「立即同步」之后归 0。没有新增任何提示文案：那个数字本身就是这句话。

刷新用静默方式，取不到状态也不弹错——裁决本身已经成功，不该因为读一次状态失败就让你以为仲裁没生效。

## 已知限制

- 裁决**不会**主动推给另一台设备，仍需要一次同步。这不是本版能改的，是同步模型的前提（见上）。本版做的是把「还欠一次」显示出来。
- 界面**没有**为此新增提示语，只有「待同步」这个数字变化。若你希望多一句文字说明，告诉我即可加（需四语言字典同改）。
- 删分组与改名撞车时仍是**两端各一条冲突**，有意的取舍，未变。
- 条目侧「本端彻底删除 + 远端更新」的同型路径仍未改，原因写在架构文档 §3.47.5。

## English summary

This release fixes one thing: after you resolve a conflict, the "pending changes" counter now updates immediately, so you can see that one more sync is still owed.

Real-device feedback on 1.6.7: on device A a folder was deleted, on device B the same folder was renamed; after syncing, both sides got a conflict. Choosing "keep local" (= confirm the deletion) on A removed the card, but the folder on B stayed until another sync ran.

Half of that is by design. Resolving a conflict is a purely local write — it bumps the tombstone version above the losing side and re-applies the deletion. No network request is made; the sync protocol has no "push the decision to the peer" channel. The other device learns about it on the next sync, exactly like any ordinary edit. Making it appear instantly would require a persistent background push connection, which contradicts the "manual sync, no background networking" design premise.

The real defect was in the UI: after resolving, the app refreshed the item list and the conflict box but not the sync status, so "pending changes" stayed at 0. With the card gone, there was nothing telling you another sync was still owed. Fixed by refreshing the sync status after a successful resolution, silently — a failed status read must not turn a successful resolution into an error message. No new text was added; the counter itself carries the meaning.

Known limits: resolving still does not push to the peer and still requires a sync; no explanatory text was added (only the counter changes); folder delete-vs-rename still produces one conflict on each device by design; the item-side equivalent path remains unfixed, with the rationale in architecture doc §3.47.5.
