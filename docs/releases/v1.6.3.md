# PasswordMS 1.6.3

这一版处理**改热键**：改不动的时候为什么改不动，以及改不动的时候为什么一声不吭。

## 「该热键已被其它程序占用」，占它的可能是自己

真机上遇到的是这样一串：想把「自动输入快捷键」改成 Ctrl+Alt+L，反复提示「该热键已被其它程序占用，请换一个组合」；换成别的键也一样。后来把上面的「全局热键」改走，自动输入键忽然又能改了；可这时想把全局热键改回原值，却什么提示都没有。

这两件事是一条链子。负责注册热键的底层组件在「撤销全部旧键」时，是**先把内部登记表清空、再逐个向系统注销**，而 Windows 这条路一旦碰到第一个失败就直接中断。于是只要中断过一次，那颗键就留在系统里，组件却已经不记得自己占着它了。从那以后，任何一次注册只要包含这颗键，系统都会回「已被注册」——我们把这句话翻成「被其它程序占用」，但占着它的其实是本程序自己。改自动输入键时，全局热键每次都要跟着一起重建，所以卡住的永远是那颗没被释放的旧键：**换多少个别的组合都没用**，因为失败的从来不是新组合。

改法是把注销做扎实：撤销旧键失败不再被静默忽略（会写进日志）；并且在注册前，对**这次要用的两个组合**各定向撤销一次。定向撤销只对本程序自己注册过的键起作用——别的程序占着的键，系统不让撤，所以这一步不会去抢别人的热键。

## 按了没反应，现在会出一句话

第二件事的成因是 Windows 的规矩：一个组合一旦被注册成全局热键，按下时按键会被系统拦走交给注册方，窗口根本收不到。所以录制新热键时，如果按的正好是已经被占用的组合，界面既不会成功也不会报错，就是没反应。

现在录制状态静置 8 秒会主动说一句：「按了没反应？这个组合已经被注册成全局热键了（可能就是本程序自己的），系统会把它拦下来，窗口收不到按键。请换一个组合。」录到东西时这句话立刻撤回，不会一边报错一边说没反应。

## 已知限制

- 这一版的改动**还没有在真机上按过**。改热键的两个毛病需要在 Windows 上实际操作一遍才作数：改一次、改回原值、再在别的程序里按一下新组合。
- **还不知道是哪一次注销失败**导致了最初那颗键残留——这需要台式机 `passwordms.log` 里 `[hotkey]` 开头的几行才能落定。修法不依赖这个答案：不管残留怎么来的，定向撤销都能把它收回来；而且下次再发生，日志里会留下「注销旧键位失败」那一行。
- 定向撤销只能收回本程序自己注册的键。组合若真是被**别的程序**占着，仍然会提示「已被其它程序占用」——这次是对的，换一个组合即可。
- 8 秒提示是解释，不是修复：真被别的程序占着的组合，还是得换一个。
- 不做两个保险库的合并（1.6.1 起的老规矩，不变）。

## English summary

This release is about **changing hotkeys**: why a change can silently stop working, and why nothing at all is shown when it fails.

On a real machine, setting the Auto-Type hotkey to Ctrl+Alt+L kept reporting "this hotkey is already used by another program", for many different combinations. After changing the main hotkey, the Auto-Type one suddenly worked again — but changing the main hotkey back gave no message whatsoever. Both symptoms come from one chain: the underlying hotkey component clears its internal registry *before* unregistering each key with the OS, and the Windows path aborts on the first error. One aborted pass leaves a key registered with the system while the component has forgotten it owns it. Every later registration that includes that key then fails as "already registered" — reported to the user as "used by another program", when the owner is this app itself. The fix unregisters the two combinations being (re)registered, one by one, right before registering them; failures to unregister are logged instead of ignored. Targeted unregistration only affects keys this process registered, so other applications' hotkeys are never taken. Separately, Windows intercepts any combination that is already a global hotkey, so the recording window never receives the key and the UI used to stay completely silent; after 8 seconds of no input it now explains that the combination is already registered and asks for another one. None of this has been verified on a real Windows machine yet, and the original leftover key's cause is still unidentified — the log line "注销旧键位失败" will identify it next time.
